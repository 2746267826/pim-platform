# PIM AI 开发工作流：需求编号、验收条件与证据规范

本文件规定**需求如何编号、验收条件如何写、证据如何留**，用于让「工单要求」与「PR 交付」逐条对得上。
配套文档：`AGENTS.md`（提交/PR/验证纪律）、`docs/qa-catalog/`（全量问题目录与测试任务书）、
`docs/module-development-guide.md`（后端模块结构）。

> 适用范围：AI 编码代理（Codeg / DSH / 其他）与独立验收方共同遵守。
> 不改变 `AGENTS.md` 既有纪律，只补「条目级可核对性」。

---

## 1. 为什么需要编号

历史上出现过三类问题，都源于「要求」与「交付」之间没有稳定的一一对应：

1. 工单写了 5 条要求，PR 只做了 3 条，**没人逐条数**；
2. PR 描述说了「已完成」，但**指不出哪条要求由哪次验证覆盖**；
3. 需求在讨论中被悄悄砍掉或改义，事后无法追溯。

解决办法：给每条要求一个**稳定编号**，让 PR、证据、复验都能引用同一个编号。

---

## 2. 需求编号（REQ）与验收条件编号（AC）

### 格式

```text
REQ-<序号>    需求条目：要做什么（用户可感知的行为）
AC-<序号>     验收条件：怎么判断它真的做到了（可执行、可观察）
```

- 序号在同一工单/需求内**从 1 开始连续**，**只增不改**；需求变更时新增编号并标注 `REQ-n（替代 REQ-m）`，不覆盖旧编号。
- 一个 `REQ` 至少对应一个 `AC`。多个 `AC` 对应同一 `REQ` 是常态（正向 + 反向）。
- 编号在**工单、PR 描述、验收记录**三处必须一致。

### 写法要求（沿用既有约定）

- **固定句型**：前提 → 我做什么 → 看到什么结果。
- **形容词黑名单**：支持 / 完善 / 优化 / 正常 / 流畅 / 合理 / 友好 / 美观。
  这类词无法判定，必须换成可观察的结果。
- **一条只判一件事**：把「登录成功且跳转正确」拆成两条。
- **必须写反面验收**：空数据不崩、旧数据不报错、越权被拒、超时可恢复等。

### 示例

```text
REQ-1 任务列表新增「进行中」状态（除已完成/未完成外）
  AC-1.1 给定一条任务，将其标记为进行中，列表徽标显示「进行中」且刷新后保持
  AC-1.2 给定进行中任务，切换回未完成，徽标恢复「未完成」
  AC-1.3 反面：旧任务（无状态字段）打开列表不报错，默认显示未完成

REQ-2 OneDrive 网格视图显示缩略图
  AC-2.1 给定含 20 张图片的目录，网格视图每格显示缩略图，非默认图标
  AC-2.2 反面：缩略图接口返回 404 时，网格降级为默认图标且不显示破损图
```

## 3. PR 中的条目映射（必须逐条给出）

PR 描述必须包含一张映射表，**每行一条 AC**，不允许「合并同类项」或省略：

```markdown
| 编号 | 实现（文件/函数） | 验证方式 | 结果 | 证据 |
|---|---|---|---|---|
| AC-1.1 | TaskListPage.tsx 徽标渲染 | 手动：改状态并刷新 | PASS | 截图/录屏（受控链接） |
| AC-1.2 | 同上 | 单测 `TaskStatusTests` | PASS | CI 运行 35491726527 |
| AC-1.3 | 同上 | 反面：旧数据 fixture | NOT-VERIFIED | 未造旧数据，待补 |
```

### 结果状态（只能用这五个）

| 状态 | 含义 | 是否允许合并 |
|---|---|---|
| `PASS` | 按 AC 执行并观察到预期结果，证据可复核 | 允许 |
| `FAIL` | 执行了但结果不符 | **不允许** |
| `BLOCKED` | 有明确阻塞（缺环境/缺权限），且已说明原因 | 需用户裁定 |
| `NOT-VERIFIED` | 没做验证，或只有间接推断 | **不允许** |
| `APPROVED-EXCEPTION` | 用户明确批准跳过，需记录批准内容 | 允许（需记录） |

- **不允许**用「已在下一步优化」「后续会补」代替状态。
- **不允许**把「测试已写」「CI 全绿」当作 AC 通过的证据——CI 绿只说明既有测试没红。
- 未运行的验证一律 `NOT-VERIFIED`，不要凭代码阅读写成 `PASS`。

### 证据规则

- 证据必须能被**独立复核**：命令 + 参数 + 输出片段；或受控链接（截图/录屏/日志片段）。
- 证据与**具体代码版本（head SHA）绑定**；新提交后沿用旧证据视为 `NOT-VERIFIED`。
- 证据不得包含明文凭据、生产数据、个人隐私字段（见 `AGENTS.md` 的凭据与生产库规则）。

## 4. 独立验收

- 验收由**开发方之外的一方**执行（独立验收身份，GitHub App），结论以 Check Run 形式发布并绑定当次 head SHA。
- 验收**必须实际执行** AC 中的验证方式，不能只读开发方的总结或 PR 描述。
- 结论语义与上表一致；服务异常或超时必须产出 `timed_out`，不得放行。
- PR 产生新提交后，旧结论自动失效，需重新验收——这是平台原生机制，无需人工记忆。
- 需求被削减、改写或跳过的，必须在 PR 中显式标注 `APPROVED-EXCEPTION` 并附用户批准内容。

---

## 5. 无工单的小改动

文档、依赖升级、格式化等无需求来源的改动，PR 中写：

```markdown
## 需求与验收映射 / Requirement & Acceptance Mapping
无 / None（无需求来源的维护性改动；验证方式见「测试」章节）
```

但仍需在「测试」章节给出实际执行的验证命令与结果。

## 6. 与既有文档的关系

| 文档 | 负责 |
|---|---|
| `AGENTS.md` | 提交纪律、分支/PR 流程、验证命令、生产库与凭据规则、既有 TDD/复核要求 |
| 本文件 | 需求编号（REQ/AC）、条目级证据映射、结果状态语义、独立验收约定 |
| `docs/qa-catalog/` | 全量问题目录与测试任务书（问题发现侧，只验不修） |
| `docs/operations/*-acceptance.md` | 各阶段功能的验收记录（历史留档） |

三者的关系：`AGENTS.md` 管「怎么做」、本文件管「怎么算做完且怎么证明」、`qa-catalog` 管「发现了哪些问题」。
