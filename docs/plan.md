# PIM 长期能力路线图

## 文档目的

这份文档是 PIM 项目的长期路线图，用来给项目主人长期查看和校准方向。

它不是 sprint 计划，也不估算时间。这个项目会以 Vibe Coding 的方式推进，很多功能要在实际使用中不断打磨，用月份或周数规划容易制造虚假的确定性。因此，这份路线图只安排功能能力的先后顺序。

路线覆盖目前已经讨论过的全部方向：

- 服务端平台与 API。
- Web 主控制台。
- Windows 后台守护程序。
- Android 后台守护程序。
- PC 活动采集与理解。
- 日历与任务。
- Today 页面。
- 快速记录板。
- 复盘与智能建议。
- 自动排程。
- Outlook / 外部日历。
- 成熟网盘与文档协作系统集成。
- 文件资料的 AI 管理层。
- 任务、日程、文件资料空间绑定。
- 未来 MCP 暴露层，让 AI 可以安全调用 PIM。

项目的核心定位是：

> PIM 是一个服务端主导的个人信息与行为智能系统。服务端是大脑，Web 是控制台，Windows 和 Android 守护程序是传感器与轻量执行器，未来 MCP 是 AI 调用入口。

## 不按时间规划

这份路线图不写“几周完成”“几个月完成”。

每个阶段只描述：

- 为什么要做。
- 要做哪些能力。
- 技术上必须做到什么程度。
- 不应该做什么。
- 做到什么程度才算完成。
- 应该为未来预留什么，但暂时不展开。

一个阶段的完成标准不是“页面能打开”，而是“这个能力可以长期使用，并且不会给后续功能埋明显的坑”。

## 总体架构原则

### 1. 服务端是系统大脑

所有长期存在的业务能力都应该在服务端处理。

服务端负责：

- 数据模型。
- 状态流转。
- 权限。
- 审计。
- API。
- 后台任务。
- 活动分类。
- 项目和上下文识别。
- 排程算法。
- 计划与实际行为对比。
- 复盘总结。
- AI 解释和建议。
- 文件索引。
- 向量化。
- 外部系统同步。
- 冲突处理。
- 重要操作确认。
- 数据重算。

Web 不应该复制服务端业务逻辑。

Web 只负责：

- 展示服务端结果。
- 收集用户输入。
- 让用户查看、筛选、确认、编辑。
- 维护少量临时 UI 状态。

例如：

- 活动分类由服务端返回，Web 不再自行分类。
- 排程方案由服务端生成和保存，Web 只展示方案并让用户确认。
- 文件搜索和 AI 理解由服务端完成，Web 只展示结果。
- 未来 MCP 也调用同一套服务端能力。

### 2. API-first / MCP-ready

系统里的所有核心能力都应该先成为服务端 API 能表达的能力。

不仅人为操作要有 API，后台自动操作、未来 AI 操作也应该有 API 或服务端能力抽象。

应该通过 API 表达的能力包括：

- 创建任务。
- 修改任务。
- 创建日程。
- 修改日程。
- 查询 PC 活动。
- 上传守护程序数据。
- 接受分类建议。
- 拒绝分类建议。
- 重算分类。
- 生成排程方案。
- 确认排程方案。
- 验证计划是否执行。
- 创建快速记录。
- 分析快速记录。
- 搜索文件。
- 恢复文件版本。
- 生成复盘。
- 生成 AI 建议。
- 同步外部日历。
- 写入外部日历。

未来 MCP server 不应该重写业务逻辑，而应该包装现有 PIM API。

API 返回值要适合未来 AI 调用，不能只返回简单的 `ok`。重要操作应返回：

- 做了什么。
- 如果是 dry-run，将会做什么。
- 影响哪些对象。
- 哪些成功。
- 哪些失败。
- 是否需要确认。
- 是否可以撤销或恢复。
- 下一步建议是什么。

危险操作必须有保护：

- 权限检查。
- 影响预览。
- dry-run。
- 用户确认。
- 审计日志。
- 可撤销或可恢复机制，至少要能恢复数据。

危险操作包括：

- 删除文件。
- 批量移动文件。
- 恢复旧文件版本。
- 批量修改任务。
- 批量修改日程。
- 写入 Outlook 或其他外部日历。
- 接受影响历史数据的大范围分类规则。
- 运行大范围重算。
- 让 AI 生成会改变大量数据的操作。

### 3. Web 是唯一主交互端

所有复杂的人机交互都在 Web 里完成。

Web 负责：

- Today 主页面。
- 日历和任务管理。
- PC 活动查看。
- 分类纠错。
- 快速记录。
- 文件浏览。
- 文件搜索。
- AI 建议确认。
- 外部日历连接状态。
- daemon 健康状态。
- 数据导入导出。
- 操作确认。

不应该为 Windows 或 Android 做另一套完整业务客户端。

### 4. daemon 是传感器和轻量执行器

Windows daemon 的职责：

- 本地登录和 token 保存。
- 采集 ActivityWatch 数据。
- 采集 KeyStats 数据。
- 上传数据到服务端。
- ActivityWatch 历史回填。
- 上报健康状态。
- 托盘显示。
- 简单手动同步。
- 简单暂停、恢复、退出。

Android daemon 的职责：

- 登录或绑定设备。
- 后台常驻。
- 采集 Android 使用统计。
- 采集前台应用时长。
- 上报设备心跳。
- 本地缓存队列。
- 网络恢复后补传。
- 低电量或省电模式下降频。
- 接收服务端简单命令，例如立即同步、暂停采集、恢复采集。
- 必要时响应通知确认。

daemon 不负责复杂业务判断。

### 5. 成熟组件优先

这个原则适用于所有功能，不只是文件资料模块。

对任何能力，都应该优先评估成熟组件、成熟协议、成熟库、成熟服务或成熟系统。只有当成熟方案无法满足 PIM 的要求时，才自研核心能力。

PIM 的要求包括：

- 服务端主导。
- API-first。
- MCP-ready。
- 数据可控。
- 隐私可控。
- 可部署。
- 可维护。
- 可扩展。
- 能和 PIM 的数据模型整合。

成熟组件优先的例子：

- 日历展示优先用成熟日历组件。
- 日历格式优先兼容 RFC 5545 / ICS。
- 文件资料优先集成成熟网盘和文档协作系统。
- 在线编辑优先集成 OnlyOffice、Collabora 或同类成熟方案。
- 向量搜索优先用成熟向量数据库、数据库扩展或搜索引擎。
- 后台任务优先用成熟 job/scheduler。
- 图表、表格、上传器、富文本编辑器优先用成熟组件。
- MCP 层优先做薄包装，不重复写业务。

自研应该有明确理由：

- 现有组件无法满足功能要求。
- 现有组件破坏服务端主导。
- 现有组件无法开放 API。
- 现有组件无法保证数据和隐私控制。
- 现有组件长期维护成本更高。

### 6. 每个功能都必须作为完整能力包完成

一个功能不是“页面写完”就完成。

每个能力包都应该包含：

- 服务端数据模型。
- 服务端 API。
- 权限和审计。
- 状态流转。
- Web 交互。
- 错误处理。
- 重要操作确认。
- 测试。
- 手动验收路径。
- 数据迁移路径。
- 部署和升级考虑。
- 未来 MCP 暴露方式。

### 7. 原始数据优先

原始数据是事实来源。

派生数据可以存在，但应该能重算。

原始数据包括：

- ActivityWatch 原始事件。
- KeyStats 原始快照。
- 用户手动创建的任务和日程。
- 快速记录原文。
- 文件元数据和版本 ID。
- 用户确认记录。
- 外部日历原始 ID。

派生数据包括：

- 活动分类。
- 项目标签。
- 计划与实际匹配结果。
- 复盘总结。
- 文件摘要。
- 向量索引。
- AI 建议。

派生数据可以缓存，但不能取代原始数据。

### 8. AI 提建议，服务端执行，用户确认风险

AI 可以帮助理解、分类、总结、推荐。

AI 不应该静默执行危险操作。

标准流程应当是：

1. 服务端收集上下文。
2. AI 生成结构化建议。
3. 服务端校验建议。
4. Web 展示影响预览。
5. 用户确认。
6. 服务端执行。
7. 服务端写入审计日志。

例如：

- AI 可以建议把快速记录转成任务，但不能直接创建大量任务。
- AI 可以建议移动文件，但不能直接批量移动。
- AI 可以建议日程提醒，但时间不明确时必须让用户确认。
- AI 可以建议分类规则，但规则生效前必须预览影响并确认。

## 推荐路线顺序

推荐长期顺序如下：

1. 可持续运行底座。
2. PC 记录事实层。
3. PC 记录理解层。
4. Today 主控制台。
5. 快速记录板基础版。
6. 日历与任务基础闭环。
7. 计划与实际行为打通。
8. 自动排程闭环。
9. 复盘与智能建议。
10. 快速记录板 AI 理解与自动归位。
11. 外部日历 / Outlook。
12. 文件资料系统 A：成熟网盘集成。
13. 文件资料系统 B：AI 文件管理层。
14. 任务、日程、资料空间绑定。
15. Android 守护程序与多设备。
16. 正式 MCP 暴露层。

注意：MCP-ready 从第 0 阶段就要开始作为 API 设计原则执行。正式 MCP server 可以放到后期。

## 第 0 阶段：可持续运行底座

### 目标

让项目可以长期迭代，不怕数据、部署、升级、日志和权限失控。

这不是“大重构阶段”，而是给后续功能加保险。

### 要做的能力

- 建立正式数据库迁移机制。
- 固定服务端启动和升级路径。
- 保持 API、Web、Windows daemon 默认地址一致。
- 增加服务端健康检查。
- 增加 daemon 健康上报。
- 增加结构化日志。
- 建立基础审计日志模型。
- 建立基础用户确认模型。
- 建立后台任务抽象。
- 建立备份与恢复文档。
- 建立本地部署验收清单。
- 为未来 MCP 工具的权限、审计、确认预留结构。

### 技术要求

- 数据库 schema 变更必须可重复、可追踪、可升级。
- 健康检查要能区分 API、数据库、存储、daemon、外部依赖。
- 服务端错误要区分用户错误、权限错误、依赖不可用和内部错误。
- 审计日志要记录操作者、操作、对象、时间、结果和来源。
- 确认模型至少支持 pending、confirmed、rejected、expired、executed。

### 不做什么

- 不因为追求完美架构而停止功能推进。
- 不重写已经可用的模块。
- 不提前做复杂工作流引擎。
- 不提前做完整 MCP server。

### 完成定义

- 新环境能稳定启动。
- 本地升级不会轻易破坏旧数据。
- 服务端和 daemon 的健康状态可查看。
- 重要操作可以审计。
- 风险操作有可复用确认模式。
- 后续功能知道在哪里加迁移、日志、健康检查和审计。

### 未来预留

- MCP 工具会复用权限、审计和确认模型。
- AI 后台任务、文件索引任务、排程验证任务都应接入同一套后台任务基础。

## 第 1 阶段：PC 记录事实层

### 目标

把“电脑上实际发生了什么”记录可靠。

在分类、AI、复盘之前，事实层必须可信。

### 要做的能力

- 保存 ActivityWatch bucket 元数据。
- 保存 ActivityWatch window 事件。
- 保存 ActivityWatch afk 事件。
- 保存浏览器页面事件。
- 保存 ActivityWatch 原始 event id。
- 保存 ActivityWatch 原始 data_json。
- 保存 KeyStats 每日兼容数据。
- 保存 KeyStats 每分钟快照。
- 计算或查询 KeyStats 分钟 delta。
- 检测采集缺口。
- 支持 ActivityWatch 历史回填。
- 提供原始数据查询。
- 提供解释时间线查询。
- 避免浏览器窗口和浏览器页面重复计时。
- 展示数据质量状态。

### 技术要求

- ActivityWatch 上传要按设备、bucket、source_event_id 幂等。
- KeyStats 样本要按设备和分钟幂等。
- 原始数据必须保留，不能只保留当前页面用到的字段。
- 解释记录要能追溯到原始记录。
- daemon 要上报最近上传时间、最近错误、队列数量、数据源可用性。
- 查询 API 要支持日期范围、设备、事件类型、应用、域名、标题、分页。

### 不做什么

- 不让 Web 计算事实。
- 不丢弃暂时不用的原始字段。
- 不伪造没有采集到的历史分钟级 KeyStats 数据。
- 不把图表显示当成事实层完成。

### 完成定义

- 用户相信 PC 记录代表真实来源数据。
- 重复上传不会产生重复事实。
- 缺失数据能被看见。
- 详情页能查看原始记录和解释记录。
- 浏览器页面和窗口不会重复计算时间。

### 未来预留

- 后续分类、计划验证、复盘、AI 建议都基于事实层。
- Android 多设备活动也应复用设备和来源元数据模式。

## 第 2 阶段：PC 记录理解层

### 目标

从“用了什么软件”升级到“我在做什么事、属于哪个项目、为什么系统这么判断”。

### 要做的能力

- 服务端活动分类器。
- 活动分类规则。
- 项目或上下文标签。
- 规则优先级。
- 内置规则。
- 用户规则。
- 低置信检测。
- 未知活动聚类。
- 分类建议。
- 接受建议。
- 拒绝建议。
- 分类重算。
- 每条分类带解释。
- URL 隐私清洗。
- 分类规则管理 API。

### 技术要求

- 分类必须由服务端计算。
- Web 只展示分类结果和纠错入口。
- 分类结果包含 category、color、projectTag、confidence、source、explanation、sourceRuleId。
- 规则条件支持 app、normalized app、domain、url path、title、window title、file path、record type、bucket type。
- AI 或系统生成的建议规则不能自动生效。
- 大范围重算必须可审计。

### 不做什么

- 不要求用户一开始手写大量规则。
- 不让 LLM 直接激活规则。
- 不把敏感 URL 原样发给 AI。
- 不在 Web 里复制一份分类逻辑。

### 完成定义

- 时间线能显示有意义的分类和项目标签。
- 未知活动会聚合成少量可处理建议。
- 用户纠错可以形成持久规则。
- 历史记录可以按新规则重算。
- 每个分类都有可解释来源。

### 未来预留

- 后续 LLM 可以生成 draft rule。
- 计划与实际行为分析会依赖分类和项目标签。
- MCP 可以暴露活动查询、分类纠错、分类建议等工具。

## 第 3 阶段：Today 主控制台

### 目标

让 Web 首页成为每天真正会打开的入口。

Today 页面应该把计划、现实、异常和下一步放在一起。

### 要做的能力

- 今日日程。
- 今日任务。
- 今日 PC 活动摘要。
- 当前数据健康状态。
- daemon 状态提醒。
- 未处理分类建议。
- 快速进入详情页。
- 计划与实际偏差入口。
- 快速记录入口。
- 服务端 Today Summary API。

### 技术要求

- Today 页面调用服务端聚合 API。
- 服务端负责解释状态。
- Web 不从多个原始接口拼业务判断。
- 空状态要说明缺少哪个数据源。
- 错误状态要能提示下一步。

### 不做什么

- 不做营销式首页。
- 不把健康提醒藏到设置里。
- 不在 Web 单独维护一套 dashboard 口径。

### 完成定义

- 打开 Web 后能看到今天计划、实际行为、异常状态、待处理事项和下一步入口。
- 数据采集失败或 API 异常能被看见。
- 用户需要确认的事情能被看见。

### 未来预留

- 每日复盘、自动排程建议、快速记录 AI 建议都应自然出现在 Today。

## 第 4 阶段：快速记录板基础版

### 目标

提供一个低摩擦入口，让用户可以先把东西丢进 PIM，而不用立刻判断它是任务、日程、资料、想法还是提醒。

### 要做的能力

- Web 右下角固定按钮。
- 点击后打开悬浮记事板。
- 可以写文字。
- 可以拖入文件。
- 可以上传文件。
- 可以保存。
- 保存后进入专门的“快速记录”板块。
- 支持列表查看。
- 支持详情查看。
- 支持编辑。
- 支持删除。
- 支持归档。
- 支持状态：inbox、processed、archived。
- 附件先走现有存储策略，未来迁移到正式文件系统。
- 所有操作都有服务端 API。

### 技术要求

- 服务端保存原文、附件、创建时间、修改时间、用户、来源、状态。
- 附件必须有稳定 ID，不能只靠路径。
- 数据结构要为后续 AI 分析预留字段。
- Web 只负责输入和展示。
- 保存操作要可靠，失败要明确提示。

### 不做什么

- 基础版不做 AI 分类。
- 基础版不自动创建任务。
- 基础版不自动创建日程。
- 基础版不要求用户选择归属。

### 完成定义

- 用户可以随时快速保存文字和文件。
- 保存内容不会丢。
- 用户可以在快速记录板统一处理。
- 记录结构足够支持未来 AI 理解。

### 未来预留

- AI 可以后续判断记录是否应转成任务、日程、提醒、资料或项目想法。
- MCP 可以把创建快速记录作为低风险写操作。

## 第 5 阶段：日历与任务基础闭环

### 目标

让任务和日程成为可靠的个人计划系统。

这里先做基础闭环，不急着做高级智能。

### 要做的能力

- 日历本。
- 任务本。
- 日程事件。
- 任务。
- 任务收集箱。
- 任务状态。
- 优先级。
- 截止时间。
- 预计时长。
- 计划开始时间。
- 拖拽任务到日历。
- 事件编辑。
- 任务编辑。
- 搜索。
- 筛选。
- 批量操作。
- ICS 导入。
- ICS 导出。
- 日历数据管理。
- 重要对象删除和恢复策略。
- 完整操作 API。

### 技术要求

- Web 的所有操作都要有服务端 API。
- 日期、时区、全天事件、重复规则要有明确约定。
- 任务和事件要有稳定 ID。
- 删除和批量修改要可审计。
- 重要写操作要为未来 dry-run 和确认模式预留。

### 不做什么

- 不把基础任务日历和自动排程混在一起。
- 不让 Web 状态决定任务或日程业务规则。
- 不提前强制任务绑定项目和资料文件夹。

### 完成定义

- 用户可以真正用 PIM 管理任务和日程。
- 数据可以导入、导出、搜索、编辑。
- API 足够完整，未来 MCP 可以读写任务和日程。

### 未来预留

- 任务和日程后续会关联 PC 活动、排程方案、复盘、文件、快速记录。

## 第 6 阶段：计划与实际行为打通

### 目标

让 PC 活动反哺日历和任务。

系统开始回答：我计划做什么、实际做了什么、差在哪里。

### 要做的能力

- 对比计划任务和实际 PC 活动。
- 对比日程和实际 PC 活动。
- 判断计划时间段是否可能执行。
- 发现未执行或被打断任务。
- 发现未计划工作。
- 发现时间被哪些活动占用。
- 建议将活动关联到任务或项目。
- 服务端生成偏差报告。
- Today 页面展示简要偏差。
- 详情页展示证据。

### 技术要求

- 匹配逻辑在服务端。
- 匹配依据包括时间重叠、分类、项目标签、应用、域名、标题、用户纠错。
- 匹配结果包含 confidence 和 explanation。
- 用户纠错应该改善后续匹配。
- 匹配结果应可重算。

### 不做什么

- 不仅凭某个 app 使用就自动判定任务完成。
- 不自动把任务标记完成。
- 不做不可逆关联。

### 完成定义

- 系统能说明计划和实际行为的偏差。
- 用户能纠正错误匹配。
- 偏差报告足够支持后续排程和复盘。

### 未来预留

- 自动排程和复盘建议都依赖这个阶段。
- AI 可以后续解释偏差原因并提出调整建议。

## 第 7 阶段：自动排程闭环

### 目标

把自动排程从算法 demo 变成可确认、可验证、可修正的真实流程。

### 要做的能力

- 选择待排程任务。
- 服务端生成多个排程方案。
- Web 展示方案对比。
- 用户确认方案。
- 确认后写入任务或日历。
- 保存排程方案记录。
- 事后用 PC 活动验证执行情况。
- 未完成任务生成重排建议。
- 记录用户反馈。
- 支持 dry-run。
- 支持撤销或恢复。

### 技术要求

- 排程生成要可解释。
- 每个方案要有指标和理由。
- 确认是服务端状态流转。
- 写入日历或任务要可审计。
- 执行验证依赖计划与实际行为打通阶段。
- 重排是建议，不是强制修改。

### 不做什么

- 不让算法直接改日历。
- 不在确认和验证闭环不成熟时追求复杂算法。
- 不隐藏方案为什么被推荐。

### 完成定义

- 排程方案可以生成、确认、写入、验证、反馈和调整。
- 用户可以信任流程，因为它有解释、有确认、有恢复路径。

### 未来预留

- AI 可以后续解释排程取舍。
- MCP 可以生成排程草案，但必须走高风险确认流程。

## 第 8 阶段：复盘与智能建议

### 目标

让 PIM 开始像个人教练一样工作。

系统不仅展示数据，还要总结现实、发现模式、提出建议。

### 要做的能力

- 每日复盘。
- 每周复盘。
- 项目投入统计。
- 分类时间统计。
- 专注与切换分析。
- 任务完成偏差分析。
- 未执行计划分析。
- 明日任务建议。
- 分类规则建议。
- 排程调整建议。
- 快速记录处理建议。
- AI 生成自然语言总结。

### 技术要求

- 复盘由服务端后台任务生成。
- 复盘要能引用证据。
- AI 输出是建议或摘要，不是事实来源。
- 发送给 AI 的上下文要最小化和清洗。
- 用户可以重新生成、忽略、确认建议。

### 不做什么

- 不让 AI 改写历史。
- 不生成没有证据的空泛建议。
- 不强迫用户每天读很长报告。

### 完成定义

- 复盘对用户有实际帮助。
- 建议可以执行。
- 用户能追溯建议从哪里来。

### 未来预留

- 文件建议、快速记录建议、MCP 读取工具都可以接入同一套复盘模型。

## 第 9 阶段：快速记录板 AI 理解与自动归位

### 目标

让快速记录板从“收纳入口”升级为“智能收件箱”。

### 要做的能力

- 分析快速记录文本。
- 分析附件元数据。
- 在文件系统成熟后分析附件文本。
- 判断是否可能是任务。
- 判断是否可能是日程。
- 判断是否可能是提醒。
- 提取时间信息。
- 提取地点或上下文。
- 建议标签。
- 建议项目。
- 建议资料文件夹。
- 建议转成任务、日程、提醒或资料。
- 用户确认后执行转换。

### 技术要求

- AI 分析在服务端执行。
- 原始快速记录保持不变。
- AI 建议必须是结构化数据。
- 时间提取要处理时区和模糊表达。
- 高风险转换必须确认。
- 接受转换后要保留回链到原记录。

### 不做什么

- 不从模糊文字直接创建提醒。
- 不在归位后删除原记录。
- 不让基础记录依赖 AI。

### 完成定义

- 系统能理解快速记录并提出合理归位建议。
- 用户确认后，服务端可以创建任务、日程、提醒或资料链接。
- 快速记录板不再只是堆东西，而是能逐步清空和整理。

### 未来预留

- MCP 可以创建快速记录并请求分析，但不直接执行高风险转换。

## 第 10 阶段：外部日历 / Outlook

### 目标

把外部日历接入 PIM，同时保持 PIM 本地计划系统的控制权。

外部日历应该丰富 PIM，而不是污染 PIM。

### 要做的能力

- OAuth 连接。
- 外部账号状态。
- 只读同步。
- 外部事件来源标记。
- 冲突检测。
- 手动同步。
- webhook 或定时同步。
- 写回外部日历。
- 写回前影响预览。
- 写回前用户确认。
- 外部写操作审计。

### 技术要求

- token 必须安全存储。
- 外部事件 ID 必须保存。
- 本地事件和外部事件必须可区分。
- 写回必须确认。
- 同步失败必须可见。
- 冲突处理必须明确。

### 不做什么

- 不静默覆盖外部日历。

### 完成定义

- 外部日历可以同步进来。
- 外部事件可以参与忙闲判断。
- 写外部日历可控、可预览、可确认、可审计。

### 未来预留

- MCP 可以通过 PIM 查询外部日历状态。
- 自动排程可以把外部忙闲块纳入考虑。

## 第 11 阶段：文件资料系统 A，成熟网盘集成

### 目标

接入成熟网盘或文档协作系统，不从零自研网盘。

文件资料系统首先要作为真实网盘可用，然后再让 PIM 做智能索引和 AI 管理。

### 要做的能力

- 选择成熟网盘或协作平台。
- 文件浏览。
- 文件夹浏览。
- 上传。
- 下载。
- 移动。
- 重命名。
- 删除。
- 回收站或恢复。
- 权限。
- 分享，如果需要。
- 尽可能多格式在线预览。
- 常见格式在线编辑。
- 版本历史。
- 恢复历史版本。
- 每次修改保留版本副本。
- 优先选择支持增量或块级版本存储的方案。
- 稳定 provider file id。
- 稳定 version id。
- PIM 服务端同步文件元数据。

### 候选方向

后续选型可以评估：

- Nextcloud / ownCloud + OnlyOffice 或 Collabora。
- Seafile，尤其适合强调块级同步和版本效率的场景。
- OnlyOffice / Collabora 作为在线文档编辑引擎，配合网盘系统使用。

选型时重点比较：

- 在线预览格式覆盖。
- 在线编辑格式覆盖。
- 版本管理模型。
- 增量或块级存储能力。
- API 能力。
- WebDAV 或其他集成能力。
- 部署复杂度。
- 数据所有权。
- 权限模型。
- PIM 是否能同步元数据和索引内容。

### 技术要求

- PIM 保存 provider、externalFileId、path、name、mimeType、currentVersionId、contentHash、timestamps。
- PIM 不能只依赖文件路径，因为文件可能移动或重命名。
- Web 里的文件操作通过服务端适配器调用网盘系统。
- 版本操作要可审计、可恢复。

### 不做什么

- 不自研网盘核心，除非成熟系统无法满足要求。
- 不自研 Office 在线编辑。
- 不把 MinIO/S3 对象存储当成完整网盘。
- 不在 AI 文件管理层成熟前自动整理文件。

### 完成定义

- 用户可以把它当真实网盘使用。
- 常见文件可以在线预览。
- 常见办公文件可以在线编辑。
- 版本历史可查看和恢复。
- PIM 可以稳定引用文件和版本。

### 未来预留

- PIM 文件索引层依赖稳定 file id 和 version id。
- 任务、日程、资料空间绑定也依赖稳定文件引用。

## 第 12 阶段：文件资料系统 B，AI 文件管理层

### 目标

让 PIM 理解文件，而不是取代底层网盘。

### 要做的能力

- 同步文件元数据。
- 提取文本。
- 生成摘要。
- 生成标签。
- 建立向量索引。
- 语义搜索。
- 按含义找文件。
- 检测重复或相似文件。
- 检测可能过期或未归档文件。
- 建议文件夹。
- 建议标签。
- 建议相关任务。
- 建议相关日程。
- 建议相关项目。
- 索引当前版本。
- 必要时索引历史版本。

### 技术要求

- 向量索引引用 file id 和 version id。
- AI 回答要能指出来源文件和版本。
- 索引任务异步执行。
- 索引失败要可见、可重试。
- 搜索和 AI 回答必须遵守权限。
- AI 只建议文件操作，用户确认后服务端执行。

### 不做什么

- 不让 AI 未确认就移动或删除文件。
- 不把敏感文件内容随意发给外部 AI。
- 不假设每个文件都能提取文本。

### 完成定义

- 用户可以按语义搜索文件。
- 系统能总结和分类文件。
- AI 能提出整理建议。
- 文件操作安全、可确认、可审计。

### 未来预留

- 文件理解结果会进入任务、日程、项目、复盘。
- MCP 可以先开放文件搜索和建议工具，再开放高风险写工具。

## 第 13 阶段：任务、日程、资料空间绑定

### 目标

把计划、活动和文件合成工作上下文。

这个阶段应该等任务、日程、PC 活动理解、文件索引都成熟后再做。

### 要做的能力

- 任务绑定资料文件夹。
- 日程绑定资料文件夹。
- 项目或上下文标签绑定资料空间。
- 根据任务推荐文件。
- 根据文件推荐任务。
- 展示工作上下文：任务、日程、文件、活动、快速记录。
- 根据 PC 活动推断当前项目。
- 用快速记录补充工作上下文。

### 技术要求

- 文件绑定使用稳定 file id，不只使用路径。
- 版本敏感场景使用 version id。
- 绑定建议由服务端生成。
- 低置信绑定需要用户确认。
- 初期不需要重型项目管理模块。

### 不做什么

- 不强迫每个任务都属于项目。
- 不用路径做唯一绑定。
- 不在文件索引和任务模型不稳定时强做绑定。

### 完成定义

- 做一个任务时，用户能看到相关日程、活动、文件和快速记录。
- 系统能建议缺失关联。
- 文件移动或改名后，绑定不轻易失效。

### 未来预留

- 复盘、AI 计划和 MCP 查询都可以利用工作上下文。

## 第 14 阶段：Android 守护程序与多设备

- 多设备时间线合并。
- 简单通知确认。
- 服务端命令：立即同步、暂停、恢复、清空队列。

### 技术要求

- 设备 ID 要稳定。
- 上传 API 复用多设备模式。

### 不做什么

- 不做完整 Android 任务 UI。
- 不做完整 Android 文件 UI。

- Android 信号可以改善计划验证和每日复盘。

## 第 15 阶段：正式 MCP 暴露层

### 目标

让 AI 可以安全调用 PIM。

MCP 层要保留服务端权威、权限、确认、审计和恢复能力。

### 要做的能力

- MCP server 包装现有 PIM API。
- 只读工具：
  - 搜索任务。
  - 搜索日程。
  - 搜索 PC 活动。
  - 搜索文件。
  - 读取 Today 摘要。
  - 读取复盘。
  - 查找相关文件。
- 低风险写工具：
  - 创建快速记录。
  - 创建任务草稿。
  - 创建日程草稿。
  - 生成建议。
- 高风险写工具：
  - 必须 dry-run。
  - 返回影响预览。
  - 创建确认记录。
  - 等待用户确认。
- 工具权限分级。
- 审计日志。
- 结构化工具返回值。

### 技术要求

- MCP 工具是服务端 API 的薄包装。
- 工具名称和 schema 稳定。
- 危险工具不能绕过确认。
- MCP 返回服务端解释和对象 ID，方便 AI 引用证据。
- 支持只读模式。

### 不做什么

- 不在 MCP server 重写 PIM 业务逻辑。
- 不开放宽泛破坏性工具。
- 不允许 AI 静默修改高价值数据。

### 完成定义

- AI 可以安全查询 PIM。
- AI 可以创建低风险输入，例如快速记录或草稿。
- 风险操作会预览、审计并等待用户确认。

## 停车场

这些想法值得保留，但不应打断主线，除非优先级变化。


- 语音快速记录。
- 桌面悬浮快速记录窗口。
- 自动文件整理后台任务。
- 跨设备通知策略。
- 多用户或家庭协作。
- 浏览器历史集成。
- 邮件接入。
- 聊天记录接入。
- 财务模块。
- 健康数据模块。
- 更完整的项目管理模块。

## 每个能力包的横向检查清单

每做一个能力包，都应该问：

- 服务端是不是事实来源？
- 每个操作是否有 API？
- 未来 MCP 能否调用，而不重写业务？
- Web 是否只负责展示、输入和确认？
- daemon 是否只负责采集、上传、状态和轻量执行？
- 是否优先评估了成熟组件？
- 如果自研，理由是否明确？
- 是否保存了必要原始数据？
- 派生结果是否可重算？
- 风险操作是否有预览或确认？
- 重要写操作是否有审计？
- 是否有权限边界？
- 是否有错误状态？
- 是否有健康状态？
