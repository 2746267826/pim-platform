## 二、逐条分诊

### S1 同类型事件不重叠 —— 服务端毫秒截断 bug（治本方案已实测验证）

**现状实测**：48h 内 715 对重叠，**100% 为 <1ms**；24h 内 146 对，146 对全部 <1ms，**≥0.1s 的真重叠 = 0**。与工单 §B-1 完全一致。

**根因（已用数据确证）**：服务端 `PcTrackerService.Tracker.cs`：
- L42 `timestamp = TruncateToMillisecond(timestamp);` —— 时间戳被截断到毫秒
- **但 `duration` 保持全精度浮点未截断**（如 `1.0193173` 秒）

于是事件结束时刻 `timestamp + duration` 落在**非整毫秒**上：

| id | 起始（已截断到 ms） | duration（未截断） | 结束时刻 |
|---|---|---|---|
| 8185 | 11:35:26.294 | 0.8231027 | 11:35:27.117**103** |
| 8186 | 11:35:27.117 | 23.1777944 | 11:35:50.294**794** |

8186 起点 `11:35:27.117000` < 8185 终点 `11:35:27.117103`，**重叠 0.000103 秒（103 微秒）**。

**决定性证据**：把 `duration` 也向下取整到毫秒（与 timestamp 同一精度）后重跑：

```sql
-- 24h 内重叠对：修复前 146 → 修复后 0
-- 48h 内重叠对：修复前 715 → 修复后 0
```

且 10078/10216 条事件的结束时刻不在整毫秒上（98.6%），说明这是**系统性**的，不是偶发。

**定性**：**写入侧 bug**，不是口径问题，也不是"相邻片段边界未严格对齐"（工单 §三 S1 的推测 A 是"客户端分段严格首尾对齐"——实测证明客户端分段本身没问题，`SessionToEvents` 产出的片段确实首尾相接；是**服务端入库时把一端截断、另一端没截断**造成的假重叠）。

**方案（推荐 A，已实测验证）**：
- **A（治本，推荐）**：服务端在 `TruncateToMillisecond(timestamp)` 的同时把 `duration` 也归一化到毫秒精度（`Math.Floor(duration * 1000) / 1000`）。**实测 48h 重叠 → 0 对**，且不改变任何用户可见时长（误差 <1ms）。
- B（口径变更）：判据引入 <0.5s 容差 —— **不推荐**：会把真实的亚秒重叠一起放过，且掩盖服务端精度不一致这个根因。

**影响面**：`PcTrackerService.Tracker.cs` 一处；需回归 `ux_tracker_events_dedup` 去重索引行为（duration 值变化会影响去重键）。**不涉及尺子口径**，可直接修。

### S2 超长事件必须拿得出活动证据 —— 客户端 idle 会话绕过 30 分钟切片

**现状实测**：6 条（工单也是 6 条，完全一致）。全部为 **存量**（09-01 ~ 09-19，均早于 T4 24h 窗口），**新增 = 0**。

构成：4 条 `idle`/`__IDLE__`（444.3m / 147.8m / 124.7m / 60.8m / 45.8m / 47.8m）+ 其余为游戏窗口。工单 §B-3 只看到 1 条（124.7m，48h 窗口内），本次按判据全窗口扫描看到全部 6 条。

**根因（代码已确证）**：`NativeTrackerService.DoPollAsync` L556-575：

```csharp
// Window resolution: check foreground window and checkpoint if long-running
if (!_sessionManager.IsIdle)          // ← idle 会话被整体跳过
{
    ...
    _sessionManager.CheckpointIfNeeded(now, window);
}
```

`CheckpointIfNeeded`（`TrackerSessionManager.cs:437-447`）本身**已经正确处理 idle**（L457-470 会重建 idle 会话），但**唯一调用点被 `if (!IsIdle)` 包住**，所以 idle 会话永不触发 30 分钟切片 —— 一次 `HandleIdleStarted` 后可以连续累积数小时成一条 idle 事件。

> 注意：这与工单 §三 S2「任务 3：如新发则定位根因」相关 —— 结论是**既有存量问题，也是仍在生效的客户端 bug**：只要用户长时间挂机一次，就会再产生一条。但因 idle 不计入活跃时长（S3 已过滤），用户可见影响有限。

**方案（纯 bug，可直接修）**：
1. 客户端 `DoPollAsync`：把 `CheckpointIfNeeded` 移出 `if (!IsIdle)` 守卫（或在 idle 分支单独调用），使 idle 会话同样按 30 分钟切片；
2. `IsScreenOff()` 已能"熄屏即刻 idle"，与切片正交。

**验收**：镜像库注入式复现 —— 模拟连续 idle 会话，验证产出多条 ≤30m 事件；存量不清理（#254 非目标）。

### S4 业务键唯一 —— 取数层分组漏字段 + 判据业务键口径不足

**现状实测**：1573 行重复（新增 36 / 存量 1537）。构成：

| 域 | 实测重复组 | 重复行 |
|---|---|---|
| PC 事件 | 0 | 0 |
| 手机定位 | 0 | 0 |
| **手机事件** | **163 组** | **179 行** |

**根因（两层，均已确证）**：

**① 取数层分组漏掉 `event_type`**（`DataReliabilityQualityInspector.cs:848,861`）：

```sql
GROUP BY device_id, package_name, event_timestamp_utc      -- ← 少了 event_type
```
判据原文（`DataReliabilityRuleCatalog` S4）要求按 `(device, package, event_time, event_type)` 唯一。取数层少了一个字段，唯一键被**放大到跨事件类型**：

| 分组口径 | 重复组 | 重复行 |
|---|---|---|
| 取数层（漏 event_type） | 1489 | **1573** ← 面板读数 |
| 判据原文（含 event_type） | 163 | 179 |

**② 判据业务键本身也漏 `class_name`**：按 `(device, package, time, type)` 仍有 163 组，但把这些行按 `class_name` 拆开 —— **0 组重复**。即这些"重复"实际是**同一时刻同一包名的多个 Activity**（Android UsageEvents 的正常现象）：

| package | event_type | 行数 | 不同 class_name 数 |
|---|---|---|---|
| com.sankuai.meituan | MOVE_TO_BACKGROUND | 5 | **5** |
| com.azure.authenticator | UNKNOWN_23 | 4 | **4** |
| com.tencent.mm | UNKNOWN_23 | 4 | **4** |

服务端写入侧 `MobileUsageIngestService.EventKey`（L783-792）的幂等键**就是** `(PackageName, EventType, EventTimestampUtc, ClassName)` —— 即**服务端认为一行数据由 class_name 区分**，而尺子判据没把 class_name 纳入业务键，导致判据与服务端写入口径**互相矛盾**。

**方案**：
- **必须修（纯 bug）**：取数层 `GROUP BY` 与 `UniqueKey` 补 `event_type` → 读数从 1573 降到 179（与判据原文一致）。
- **需拍板（判据口径变更）**：把 `class_name` 纳入手机事件业务键，并在 `DataReliabilityRuleCatalog` 的 `Criterion` 原文同步更新（当前原文为 `(device, package, event_time, event_type)`）。理由是**与写入侧幂等键对齐**——否则尺子会永远报 163 组"假重复"。若拍板同意，**新增重复归零**。

**影响面**：`DataReliabilityModels.BusinessRecordKey.ForMobile`、`DataReliabilityInvariants.CheckS4`（去重键）、取数层 SQL、规则总表判据原文、前端面板文案、相关单测。属**判据口径变更**，按工单 §2.2 需先拍板。

### S6 设备必须自己声明下线 —— 判据三处缺陷

**现状实测**：73 处（全新增），与工单完全一致。

**根因（逐条确证）**：

**① 空档按"相邻事件起始时刻之差"计算，而非"上一事件结束 → 下一事件开始"**（`DataReliabilityInvariants.cs:805-811`）：

```csharp
var t1 = sortedTimes[i];
var t2 = sortedTimes[i + 1];
var gapMinutes = (t2 - t1).TotalMinutes;   // ← 起点减起点，忽略了前一个事件的 duration
```

判据原文写的是「设备**停止出数**必须自己有交代」——停止出数发生在事件**结束**时刻。实测差异：

| 口径 | 判定为 >30m 空档的处数 |
|---|---|
| 现状（起点差） | **72** |
| 应为（结束→下一起点） | **29** |

即 **73 处里有 43 处是判据自己算错造成的假阳性**。

**② 上传滞后 p99 把合成 gap 事件算进"链路延迟"**：p99 实为 **425.9 分钟**（7 小时）。按事件类型拆开：

| event_type | n | p50 | p99 | max |
|---|---|---|---|---|
| **gap**（合成） | 148 | **305.9m** | **782.6m** | 812.6m |
| idle | 188 | 7.2m | 147.8m | 444.2m |
| web-page | 4516 | 1.3m | 16.1m | 133.4m |
| window | 5364 | 0.6m | 22.3m | 537.1m |

**排除合成 gap 事件后，p99 = 19.2 分钟**（< 30m 阈值，合规）。gap 事件的 `timestamp` 是**断档起点**、`created_at` 是**重启后补传时刻**，两者之差天然等于断档时长，**不代表上传链路延迟**。判据引用 6 处（`DataReliabilityInvariants.cs:839-870`）因此虚增违规。

**③ 上传样本未按时间窗限定**：取数层取全表 `MaxScanRows` 行（`ORDER BY timestamp DESC LIMIT 20001`），把 8 月底的历史延迟也计入 p99。

**④ 下线声明数据源接线错误**：`CheckS6Async` 读 `pc_tracker_health`（当前只有 **1 行**、无历史序列），而**真正的离线声明在 `daemon_heartbeats`**（有 `planned_offline_at` / `offline_reason` 字段，实测 PC 有一条 `exit` 声明）。判据引用的"缺失历史心跳时序与离线声明日志"其实**存在**，只是没接线。

**方案**：
- **纯 bug（可直接修）**：① 改为「上一事件结束（滚动最大值）→ 下一事件起点」；③ 上传样本限定体检窗口；④ 改读 `daemon_heartbeats`（或两者合并）作为声明数据源。
- **需拍板**：② gap 事件是否应排除出上传滞后的分子 —— 建议**排除**（gap 是系统自己生成的合成事件，其"延迟"无意义），并同步更新判据原文的说明。

### S7 断档必须在时间轴上被标记 —— 判据不看 gap 事件

**现状实测**：41 处未标记空洞（工单 39，同量级）。**全部为存量**：按日分布 08-31 ~ 09-20，最大 1466 分钟。

**根因（代码已确证）**：`CheckS7_TimelineGapMarked`（`DataReliabilityInvariants.cs:896-938`）拿到区间列表后：

```csharp
for (int i = 0; i < list.Count - 1; i++)
{
    var a = list[i]; var b = list[i + 1];
    if (b.StartTime > a.EndTime)
    {
        var holeMinutes = (b.StartTime - a.EndTime).TotalMinutes;
        if (holeMinutes > thresholdMinutes) { /* 判违规 */ }
    }
}
```

它**只用"相邻两条区间收尾是否相接"来认定空洞**，完全**没有检查这个空洞是否已被 gap 事件覆盖**。但判据原文明确要求：「空洞必须被『缺数据』类事件（gap 或等价标记）**完整覆盖**」。

取数层（`CheckS7Async`）其实**已经把 gap 事件查出来了**（`WHERE event_type IN ('window','idle','gap')`）并设置了 `IsGap` 字段，但判据**从头到尾没有读 `IsGap`**——该字段是**死字段**。所以：一个被 gap 事件完美覆盖的断档，仍然被判"未标记空洞"。

**决定性证据**：把 gap 事件合并成区间后再检查覆盖率：

| 指标 | 值 |
|---|---|
| 空洞总数 | 2940 |
| >30m 空洞 | 29 |
| **>30m 空洞被合并 gap 区间完整覆盖** | **0** |
| >30m 空洞未被覆盖 | 29 |

即**当前 gap 事件确实一处都没盖住 >30m 的空洞** —— 所以"未标记"的**结论**碰巧成立，但**推理过程是错的**（判据从未做覆盖检查，是蒙对的）。这条尺子现在**无法区分"有 gap 标记"和"没有 gap 标记"**。

**另一个残留问题**：即便判据正确实现覆盖检查，gap 上报本身也不完整。实测 09-16 起客户端开始上报 gap（09-16: 28 条 / 09-17: 35 / 09-18: 29 / 09-19: 23 / 09-20: 21），但**覆盖仍为 0**：gap 分片与相邻事件的区间在边界上不完全对齐，且上报的 gap 只覆盖了部分断档。

**方案**：
- **纯 bug（可直接修）**：判据实现真正的覆盖检查 —— 把 `IsGap` 区间合并后，判别一个空洞是否被 gap 区间完整覆盖；未覆盖才算违规。
- **需拍板**：阈值为 15 分钟，但 gap 分片按 **1800 秒（30 分钟）** 切块（`NativeTrackerService.EnqueueGapChunks` L317-318），所以单个 gap 分片最长 30 分钟。对超长断档，客户端会上报多个首尾相接的 30 分钟分片——合并后可以覆盖。**但客户端只在"启动/恢复/退出"时上报 gap**，运行中崩溃的断档无标记。是否要求客户端在运行中也补齐，需要拍板。

### S9 有缺口必有信号 —— 数据源缺失 + 分母口径缺陷

**现状实测**：`⚪ UNKNOWN`，近似覆盖率 27.4%，备注「数据源不足」。与工单一致。

**根因（逐条确证）**：

**① 分子跨设备求和，却归属单一设备**（`DataReliabilityQualityInspector.cs:1230-1241`）：

```sql
SELECT COALESCE(SUM(duration), 0) FROM pc_tracker_events
WHERE timestamp >= @since AND event_type IN ('window','web-page') AND is_idle = false;
-- 没有 GROUP BY device_id / 没有 device 过滤
```

而 `deviceId` 单独从 `pc_tracker_health` 取"最新一行"。多设备时分子是**全设备和**，却记在**一台设备**名下。

**② 分母硬编码为 86400 秒（24h 自然窗口）**：注释自己承认「若粗暴以 24h 自然日 86400s 为分母，夜间关机 14h 将导致覆盖率虚低 47.7%」，于是干脆置 `IsDataInsufficientForDenominator = true` **放弃判定** —— 这就是"自己判不了"的直接原因。

**③ 数据源其实存在，只是没接线**：判据引用的"缺失历史心跳序列与离线声明日志"**确实存在**：
- `daemon_heartbeats`（有 `received_at` 心跳序列、`planned_offline_at`/`offline_reason` 离线声明）
- `pc_tracker_events` 的 **gap 事件**本身就是设备自己声明的"这段没数据"

**已实测可行的分母口径**（3 种，均落在真实数据上）：

| 分母口径 | 24h 覆盖率 | 判定 |
|---|---|---|
| 24h − 合并 gap 区间（设备声明的离线时长） | **99.3%** | 🟡 黄（95%~99% 之间 → 实为 99.3% 接近绿） |
| 24h − 合并 gap 区间，分子只算活跃（排除 idle） | 69.4% | 🔴 红 |
| 已记录时长 ÷（已记录时长 + 未解释空洞） | **99.86%** | 🟢 绿 |

**方案（需拍板）**：
- **推荐口径**：分母 = 24h 窗口 − 设备自己声明的离线时长（合并后的 gap 区间 ∪ `daemon_heartbeats.planned_offline_at` 覆盖段）；分子 = 有效数据时长（window/web-page/idle，即"有记录"的时长）。这样"没记录"与"声明过没记录"被区分开，正是判据原文的意图。
- 取数层需：按 `device_id` 分组；接 `daemon_heartbeats`；仅当分母仍无法界定（既无心跳也无 gap 声明）时才输出 UNKNOWN。
- **拍板点**：分母用「窗口 − 声明离线」还是「记录时长 + 未解释空洞」？两者的差别在于**未声明空档**算不算"在线但没记录"。前者会把它算成在线（从而拉低覆盖率、报红），后者不会。按判据原文「覆盖率 = 有效数据时长 ÷ 设备在线时长」+「没有声明就突然停止 30 分钟，说明采集端崩溃或掉线」，**前者更符合原意**（未声明空档 = 在线却没数据 = 应该报红）。

### S13 实例唯一 —— 判据判定条件与判据原文不符

**现状实测**：2 处（与工单完全一致）。

**根因（已确证）**：判据原文（`DataReliabilityRuleCatalog` S13）：

> 同一 device_id 在任一时刻只应有一条独立采集流，按 instance_id **或互斥的轮询相位**判定。
> 阈值：同一小时内出现 ≥ 2 条**互斥**采集流判红。

而 `CheckS13_SingleInstance`（`DataReliabilityInvariants.cs:1421-1441`）的实现是：

```csharp
var instanceIds = g.Select(h => h.InstanceId).Where(...).Distinct().ToList();
if (instanceIds.Count >= 2)   // ← 只看"一个小时内出现过 ≥2 个不同 instance_id"
{ /* 判红 */ }
```

**只数"一个小时里出现过几个不同 instance_id"，完全不做时序重叠判断**。因此一个"旧进程退出、新进程接管"的**正常重启**也会被判红。**"互斥"这个关键词在实现里没有任何对应逻辑。**

**两个被标记的案例实测**：

| 案例 | 时刻 | 实测 |
|---|---|---|
| A | 09-18 19:00 | 旧实例最后一条 19:17:12.038（+10s=19:17:22.038），新实例第一条 19:17:22.039 —— **交接误差 0.001 秒，重叠对 = 0** |
| B | 09-03 09:00 | 单条 `25a9856e…`（zcode，70s，09:00:50.963），与 `mnmlnali…` 的下一段重叠 **0.000310 秒** —— 即 §二 S1 的同一毫秒截断效应 |

- **A 是客户端升级/重启的正常接管，不是多实例并发** —— 假阳性。
- **B 与 S1 同源**（毫秒截断造成的 310 微秒假重叠），修掉 S1 后自动消失。

**另注**：判据里的"轮询相位"分支是**死代码** —— 取数层 `CheckS13Async`（L1536-1541）从未设置 `PhaseOffsetSeconds`（恒为 0），而分支要求 `phases.Count >= 2`，永不成立。

**方案（纯 bug，可直接修）**：
1. 判据改为按**时序重叠**判定：同一 device 内，不同 instance_id 的区间是否存在真实时间重叠（含最小容差，与 S1 修复后的精度一致）→ 有重叠才算"并发采集流"；
2. 一个小时内 ≥2 个 instance_id 但**无重叠**（正常交接）→ 不判红（可降为观察项或直接通过）；
3. 轮询相位分支：要么接线（取数层补 `PhaseOffsetSeconds`），要么按判据原文保留但明确标注未接线。**建议删除死分支并在判据原文注明当前按 instance_id + 时序重叠判定**（属口径澄清，一并拍板）。

**验收**：镜像库复测 —— 案例 A 不再判红；案例 B 随 S1 修复消失；48h 内同小时真并发 = 0。

## 七、复审轮次记录（Codex CLI 对抗式复审）

按要求反复调用 Codex CLI 复审直到无阻塞项。实际经过 **4 轮**，每轮都发现并修复了真实缺陷：

| 轮次 | 发现 | 性质 |
|---|---|---|
| 1 | S1 历史全精度行与归一化后上传无法去重；S13 漏检跨整点重叠；导出通路漏拷容差配置；多实例零时长不可判定；NaN 绕过阈值校验 | Important ×4 + Minor ×2 |
| 2 | S6 一次 `exit` 声明被当成"此后永久离线"（实测 7 秒后就恢复出数）→ 会掩盖之后所有真实断档；S7 区间基准排除 `web-page` → 6 处幻影空洞 | Critical ×1 + Important ×1 |
| 3 | S9 设备集合漏掉"只有 gap、没有记录"的设备；S9 分子 `SUM(duration)` 重复累加重叠事件且整段计入跨窗口事件；S7 1 秒容差过宽 | Important ×2 + Minor ×1 |
| 4（自查 + 复审） | **S7 覆盖检查原本是不可达死代码**（gap 与时间线混在同一列表）；S7/S9 缺数据类型口径不一致；仅 1 个阈值做了有限值校验；S9/S7 大小写语义不一致（Postgres `varchar IN` 大小写敏感，C# 用 OrdinalIgnoreCase） | Critical ×1 + Important ×2 + Minor ×1 |

### 其中两个特别值得记录的发现

1. **S7 覆盖检查是不可达死代码**：上一轮"实现真正的覆盖检查"时，gap 区间与真实事件被放进
   同一个时间线列表，逻辑上自相矛盾 —— 能覆盖空洞的 gap 区间本身也在列表里，会把空洞
   "填掉"，`holeStart < holeEnd` 永不成立。改为**双输入设计**（时间线 = 非 gap 事件；
   覆盖标记 = gap 区间）后覆盖检查才真正可达。实测：53 处空洞中 11 处被 gap 完整覆盖。
2. **大小写语义不一致**：C# 用 `OrdinalIgnoreCase`，而 PostgreSQL 的 `varchar IN (...)` 
   大小写敏感。一旦出现大写 `GAP`，S7 判为"缺数据"、S9 却算作"有效记录"。
   已改用 `LOWER(event_type)` 统一，并把缺数据类型收敛为**单一权威清单**，
   使 SQL 与 C# 两份口径在结构上不可能漂移。

### 测试反驳性（均已实测）

- 回退 S7 双输入设计 → 2 条用例失败（含专门覆盖"旧实现把 30 分钟空白切成两段不达标的
  碎片从而漏报"的用例）；
- 去掉 `IsFinite` 校验 → 相关用例失败；
- 只改 C# 侧缺数据类型集合 → 漂移断言失败；
- 移除 `LOWER()` → 大小写语义断言失败；
- 去掉 S1 历史行归一化 → 去重回归用例失败；
- 真库取数 SQL 烟测能抓住开发中真实发生过的 CTE 逗号语法错误
  （`RecordingDbConnection` 只记录 SQL 文本、从不执行，这类错误在既有单测里全绿）。

## 八、观察项（建议开 issue，不在本单范围）

1. **S9 `ReportedStatus` 时效性**：S9 判的是"缺口有没有产生信号"，因此覆盖率 60% 但设备
   如实上报 `Error` 时通过。若设备状态字段长年固定为 `Error`、不再更新，这条尺子无法区分
   "如实报告"与"状态上报本身也坏了"。需引入状态上报时效性判定（口径变更）。
2. **S7 客户端运行中补齐 gap**：客户端只在启动/恢复/退出时上报 gap，
   运行中崩溃造成的断档在时间轴上没有标记。判据已能正确识别这种"无标记空洞"，
   但要在数据侧消除需改客户端（需 Windows 实机验证）。
3. **S2 客户端 idle 会话 30 分钟切片**：`NativeTrackerService.DoPollAsync` 的
   `if (!_sessionManager.IsIdle)` 守卫使 idle 会话永不触发 `CheckpointIfNeeded`。
   `CheckpointIfNeeded` 本身已支持 idle，只需把调用移出守卫。需 Windows 实机验证。
4. **空载批次参与覆盖判定**（工单 §五-1）：`MobileGapService` 只看
   `failed_count=0 且 completed`，历史空载批次仍被当"覆盖窗口"。
5. **客户端同步自监控**（工单 §五-2）：日志 2 天即滚失，秒级同步循环无人察觉。
6. **S11 取数扫描上限**（工单 §五-3）：取数无时间窗（`LIMIT MaxScanRows`），表增长后复查。
7. **Ruler S9 分母未纳入 `daemon_heartbeats` 心跳序列**：当前分母只用 gap 声明。
   若要更精确（区分"设备在线但采集端没记录"与"设备根本不在线"），
   可接入 `daemon_heartbeats.received_at` 序列——该表目前每设备每 daemon 仅一行，
   需要先改写入侧保留历史。
