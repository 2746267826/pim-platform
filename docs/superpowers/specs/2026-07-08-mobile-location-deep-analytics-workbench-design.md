# 手机记录与历史位置深度分析工作台设计

日期：2026-07-08

## 背景

手机上传链路已经能提供可用数据，但当前两个页面仍然偏“原始记录浏览器”：

- `手机记录` 页面已经具备近 7 天、总时长、分类占比、Top App、时间线和 App 分类管理，但热力图把每个桶渲染成重复的小时数字，缺少日期轴、小时轴、强度图例、选中详情和下钻语义，视觉上像一整面数字墙。
- `历史位置` 页面主要是筛选、地图和定位点列表。它能展示点，却不能回答“这段时间去了哪里、停留多久、移动了多远、哪些点可信、哪些是噪声”。
- App 可读性仍受包名影响。用户要先理解 `com.tencent.mobileqq`、`com.ss.android.ugc.aweme` 这类技术标识，才能理解自己的行为。
- 大量记录不应直接挤进第一屏。页面应先展示聚合结论，再允许下钻到会话、事件、定位原始点。

本设计选择深度分析路线 C：不按开发时间收缩范围，以一个完整、可演进的“移动行为分析工作台”为目标，统一处理手机使用记录与历史位置记录。

## 最终验收目标

这部分用于后续 goal 模式验收。只有同时满足以下目标，才算该阶段完成：

1. `手机记录` 默认以北京时间展示近 7 天，并在顶部保留 `今天 / 7天 / 30天 / 自定义` 快捷切换。
2. `历史位置` 默认以北京时间展示近 7 天，并与手机记录使用同一套时间范围、设备、质量筛选视觉语言。
3. 手机记录热力图不再显示重复小时数字墙，而是清晰的 `日期 × 小时` 矩阵：左侧日期、顶部小时、格子表示使用强度、图例表示强弱、点击后在详情面板展示该时段构成。
4. 热力图支持按小时、30 分钟、15 分钟下钻，但下钻发生在选中详情或局部视图中，不让全局页面突然缩到一个小时间段。
5. 手机记录首页优先展示中文 App 名称和生活分类；包名只作为辅助信息或诊断信息。
6. 手机记录提供至少以下聚合：总使用时长、日均、峰值日、峰值小时、App 数、切换次数、完整度、最近同步、分类占比、Top App、日趋势、小时分布、异常提示、目标进度。
7. 手机记录时间线默认展示“行为块”，例如 `20:00-21:00 短视频/娱乐 52分钟`，并可继续展开到会话和原始事件。
8. 历史位置首页优先展示轨迹地图、停留点、移动片段、位置质量和选中片段详情；原始定位点列表不再占据主视觉。
9. 历史位置提供至少以下聚合：定位点数量、保留点数量、活跃跨度、估算里程、停留点数量、最长停留、平均误差、质量提示、移动/停留时间线。
10. 历史位置支持地图图层：轨迹线、停留点、误差圈、低质量点、原始点明细。
11. 两个页面所有新增可见 UI 文案以中文为主，允许少量技术字段如 `GPS`、`App`、`UTC`、包名作为辅助内容。
12. 所有新增设计和实现避免卡片套卡片、过度装饰和营销式 hero；后台工具应保持密集、清晰、可扫读。
13. Web 构建通过 `npm --prefix src/client-web run build`。
14. 后端或接口变更通过 `dotnet test Pim.sln`。
15. 推送到 `master` 后等待 GitHub Actions 自动构建，并确认相关构建成功；如果外部环境失败，最终说明必须给出具体失败项和是否与本次变更有关。
16. 最终页面必须贴近本规格的“已验收 UI 基线”。后续计划和实现不能只保留“工作台”概念而改变主要画面结构、第一屏信息顺序、热力图语义、历史位置地图与详情的左右关系。

## 设计方向

采用深度分析工作台，而不是轻量修补。

核心原则：

- 先看模式，再看明细。
- 先显示人能理解的中文名称、分类、时间段、地点语义，再保留包名、原始事件、原始坐标用于排查。
- 手机使用和位置轨迹使用同一套顶部筛选、指标卡、主视图、右侧详情、下方时间线结构。
- 北京时间是默认日历边界。UTC 只用于接口、数据库和诊断。
- 点选、筛选、下钻都应可撤销；用户不会因为点了一个热力格就失去原来的 7 天视野。
- 数据质量必须可见。完整度、缺口、低精度、过期聚合、系统噪声隐藏都不能默默发生。

视觉伴随草案已经验证基本布局：左侧沿用现有导航，页面主体为顶部筛选、指标条、主工作区、辅助图表和明细列表。该草案已经被用户确认为“大致符合要求”，因此下方“已验收 UI 基线”是后续计划和实现的视觉契约。允许按现有组件体系微调间距、颜色和响应式细节，但不得改变主要信息层级和交互语义。

## 已验收 UI 基线

本节是计划阶段和实现阶段的硬约束。后续开发计划必须逐项映射到这些 UI 单元，不能只写“重构页面”“优化热力图”这类抽象任务。

### 总体画布

页面延续当前 PIM 后台应用结构：

- 左侧固定导航栏，桌面宽度约 224px，保留 `PIM`、`个人中枢`、健康状态、主导航项。
- 当前 mockup 中 `手机记录` 导航项高亮；实际页面分别在 `手机记录` 和 `历史位置` 路由中高亮对应导航。
- 主内容区背景是浅灰蓝，页面内容是白色一层面板，不做营销式大标题，不做装饰性渐变背景。
- 页面内容以“后台工作台”密度呈现，桌面端 1440px 到 1500px 宽度下第一屏应能看到顶部筛选、指标、主视图和右侧详情。
- 面板圆角不超过 8px；只使用一级面板、指标卡、重复列表项和详情块，不做卡片套卡片。
- 中文是默认展示语言。技术字段如 `GPS`、`App`、`UTC`、包名只出现在辅助信息或诊断字段中。

### 共享顶部结构

`手机记录` 和 `历史位置` 顶部必须使用同一种结构：

1. 页面标题区在左：标题一行，说明文字一行。
2. 快捷操作区在右：`今天 / 7天 / 30天 / 自定义` 分段控件、`北京时间` 标识、`刷新` 主按钮。
3. 默认选中 `7天`，选中态为深色底白字；未选中态为浅底深字。
4. `刷新` 是蓝色主按钮；`北京时间` 是普通按钮或状态标识，不应隐藏在下拉菜单里。
5. 顶部高度应紧凑，避免把第一屏推下去。

顶部文案示例：

- 手机记录标题：`手机记录`
- 手机记录说明：`从“包名列表”转成“可解释的使用行为”。热力图只显示强度，日期和小时作为坐标轴。`
- 历史位置标题：`历史位置`
- 历史位置说明：`从“地图 + 点列表”升级为“轨迹、停留、质量、选中详情”一屏完成。`

### 共享筛选条

筛选条紧贴顶部结构下方。桌面端为 6 列，窄屏为 2 列或 1 列。

手机记录筛选项按顺序为：

1. `设备`：例如 `Pixel 8 Pro`。
2. `分类`：例如 `全部分类`。
3. `App`：占位 `搜索名称或包名`。
4. `噪声`：例如 `隐藏系统噪声`，右侧显示 `开`。
5. `粒度`：例如 `小时视图`。
6. `范围`：例如 `7月2日 至 7月8日`。

历史位置筛选项按顺序为：

1. `设备`：例如 `Pixel 8 Pro`。
2. `范围`：例如 `7月2日 至 7月8日`。
3. `最大误差`：例如 `50 米以内`。
4. `展示`：例如 `轨迹 + 停留点`。
5. `质量`：例如 `隐藏已拒绝点`，右侧显示 `开`。
6. `搜索地点`：占位 `地点或坐标`。

筛选控件视觉要求：

- 标签为小号灰色粗体。
- 控件高度约 36px，圆角 8px，边框浅灰，文字不溢出。
- 下拉类控件右侧显示箭头或等价图标。
- 搜索框必须保留可输入形态，而不是只显示静态文本。

### 共享指标区

两个页面第一屏都必须有 6 个指标卡。桌面端为 6 列，窄屏为 2 列或 1 列。

指标卡结构：

- 顶部小标签，例如 `总使用时长`。
- 中间大数字，例如 `73小时23分`。
- 底部辅助说明，例如 `较上期 0%`。
- 重要提醒卡使用浅黄色背景和黄色边框，例如 `目标`、`质量提示`。

手机记录指标卡按顺序为：

1. `总使用时长`：示例 `73小时23分`，辅助 `较上期 0%`。
2. `日均`：示例 `10小时29分`，辅助 `峰值 7月5日`。
3. `目标`：示例 `未设置`，辅助 `可配置每日目标`，使用提醒样式。
4. `App 数`：示例 `87`，辅助 `切换 7,346 次`。
5. `完整度`：示例 `68%`，辅助 `事件覆盖 69%`。
6. `最近同步`：示例 `7月8日`，辅助 `00:12 生成`。

历史位置指标卡按顺序为：

1. `定位点`：示例 `428`，辅助 `保留 391 个`。
2. `活跃跨度`：示例 `6天18时`，辅助 `缺口 2 段`。
3. `估算里程`：示例 `84.6 km`，辅助 `按轨迹片段估算`。
4. `停留点`：示例 `12`，辅助 `最长 3小时20分`。
5. `平均误差`：示例 `18 m`，辅助 `GPS / 网络混合`。
6. `质量提示`：示例 `2 条`，辅助 `有低精度密集点`，使用提醒样式。

### 手机记录第一屏布局

手机记录第一屏必须保持以下结构：

1. 顶部标题与快捷操作。
2. 6 列筛选条。
3. 6 个指标卡。
4. 主工作区，左侧是 `使用热力图`，右侧是 `选中时段`。
5. 主工作区下方是 `分类占比` 和 `Top App` 两个并列图表。
6. 再下方是 `使用时间线`。

桌面端主工作区使用两列：

- 左列 `使用热力图` 占主要宽度。
- 右列 `选中时段` 宽度约 360px。
- 两列间距约 14px。
- 两列顶部对齐。

### 手机记录热力图视觉细节

热力图必须按 mockup 的阅读方式实现：

- 面板标题为 `使用热力图`。
- 说明文字为 `左侧是日期，顶部是小时。格子不再重复写小时，点击后在右侧查看分类和 App 明细。`
- 右上角显示图例：`少`、渐变条、`多`。
- 热力图容器允许横向滚动，但不允许整页因为热力图撑爆。
- 热力图最小宽度约 920px，左侧日期列约 92px，后面 24 个等宽小时列。
- 第一行是小时轴：`0` 到 `23`。
- 后续每行是日期：例如 `7月2日 周四`、`7月3日 周五`、`7月4日 周六`、`7月5日 周日`、`7月6日 周一`、`7月7日 周二`、`7月8日 今天`。
- 格子高度约 26px，间距约 4px，圆角约 5px。
- 空闲或睡眠格为近白浅灰；低强度为极浅青；中强度为浅青绿；高强度为青绿；峰值为深青绿。
- 不完整或质量警告格在底部显示黄色细条。
- 选中格使用深色 2px 描边或等价强选中态。
- 格子内部默认不显示小时数字；可以在 hover tooltip、详情面板或辅助技术属性中显示具体时间。

禁止事项：

- 禁止把每个桶渲染成写着 `0`、`1`、`2` 的重复数字块。
- 禁止按分类拆分后直接把同一小时渲染成多格，导致坐标重复。
- 禁止在默认 7 天视图中直接渲染 30 分钟或 15 分钟全量网格。

### 手机记录右侧详情

右侧详情面板标题为 `选中时段`，默认展示当前选中热力格。

结构必须包含：

1. 面板头部：标题 `选中时段`、时间范围，例如 `7月6日 20:00 至 21:00`、状态 chip，例如 `高峰`。
2. 大数字：例如 `52分钟`。
3. 分类 chip：例如 `短视频/娱乐`、`社交通讯`、`质量正常`。
4. 2 × 2 小指标区：
   - `Top App`：例如 `抖音`。
   - `切换`：例如 `43 次`。
   - `最长连续`：例如 `18分钟`。
   - `系统噪声`：例如 `已隐藏`。
5. App 构成条：
   - `抖音`：例如 `34分钟`。
   - `微信`：例如 `11分钟`。
   - `QQ`：例如 `7分钟`。
6. 说明提示：`点击热力格后，不再把全局范围缩到单格导致页面“跳走”；右侧展示明细，下面的图表和时间线可选择是否跟随联动。`

这个面板不是可选项。它是解决热力图可读性的核心，计划中必须独立列出实现和测试。

### 手机记录下方图表

- 左：`分类占比`
- 右：`Top App`

`分类占比` 使用横向条形图，示例顺序：

- `短视频/娱乐`，`22小时17分`
- `社交通讯`，`20小时29分`
- `未分类`，`15小时12分`
- `购物/外卖`，`1小时27分`

`Top App` 使用横向条形图，必须展示中文名和辅助包名：

- `抖音`，辅助 `com.ss.android.ugc.aweme`
- `小红书`，辅助 `com.xingin.xhs`

- `微信`，辅助 `com.tencent.mm`

条形图必须使用不同强调色区分类别或序列，但整体保持克制，不能变成单一大色块。

### 手机记录时间线

`使用时间线` 位于图表下方，标题说明为 `按连续行为块展示，避免一次性塞入 500 条原始事件。`

默认展示行为块列表，示例：

桌面端主工作区使用两列：

### 历史位置地图视觉细节

地图面板标题为 `轨迹地图`。

说明文字为 `地图优先占据主视野；右侧同步显示选中片段、停留点和质量。`

面板右上角显示图层 chip：

- `路线`
- `停留`
- `误差圈`

地图内部必须有以下视觉层：

- 地图底图或降级底图。真实实现使用 Leaflet/OpenStreetMap；底图失败时用浅色网格和轨迹摘要降级。
- 轨迹线：主路线使用蓝色实线。
- 辅助或低可信路线：使用青绿色虚线。
- 停留点：使用橙色较大圆点。
- 普通定位点：使用蓝色小圆点。
- 选中片段或选中点：使用玫红圆点加外发光或等价明显选中态。
- 地图左上覆盖摘要徽标：例如 `轨迹 84.6 km`、`停留 12 处`、`平均误差 18 m`。
- 地图右下角显示比例尺，例如 `2 km`。

地图是主视觉，不允许退回“上面一小块地图 + 右侧长点列表”的旧结构。

### 历史位置右侧详情

右侧详情面板标题为 `选中片段`，默认展示当前选中的移动片段或停留点。

结构必须包含：

1. 面板头部：标题 `选中片段`、时间范围，例如 `7月7日 18:20 至 19:05`、状态 chip，例如 `移动中`。
2. 大数字：移动片段显示距离，例如 `7.8 km`；停留片段显示时长，例如 `3小时20分`。
3. 2 × 2 小指标区：
   - `耗时`：例如 `45分钟`。
   - `点数`：例如 `36`。
   - `平均速度`：例如 `10.4 km/h`。
   - `平均误差`：例如 `14 m`。
4. 主片段卡：
   - 标题示例 `公司附近 → 地铁站`。
   - 质量标记示例 `高质量`。
   - 一条分段颜色条，用于表达 GPS、网络、低质量或停留构成。
   - 说明示例 `GPS 为主，网络点 3 个。可查看原始点。`
5. 相关停留卡：
   - 标题示例 `停留：公司附近`。
   - 时长示例 `3小时20分`。
   - 说明示例 `18 m 半径内 94 个点，时间连续。`
6. 说明提示：`点列表不再作为主视觉；默认折叠为“原始点明细”，用于排查质量和同步问题。`

### 历史位置下方列表

地图下方第一行是两个并列面板：

- 左：`停留与移动时间线`
- 右：`原始点明细`

`停留与移动时间线` 说明为 `将原始定位点聚合成用户能理解的片段。`

示例行：

- `09:10-12:30`、`停留：公司附近`、`94 个点 · 平均误差 12 m`、`3小时20分`
- `18:20-19:05`、`移动：公司附近 → 地铁站`、`36 个点 · 7.8 km`、`45分钟`
- `19:12-20:40`、`停留：商圈`、`42 个点 · 低精度 3 个`、`1小时28分`

`原始点明细` 说明为 `保留排查能力，但不让它占据第一屏。`

表格列必须至少包含：

- `时间`
- `来源`
- `误差`
- `质量`

示例行：

- `19:04:22`、`GPS`、`9 m`、`高`
- `19:02:10`、`GPS`、`12 m`、`高`
- `18:58:41`、`网络`、`44 m`、`可用`
- `18:49:33`、`网络`、`83 m`、`隐藏`

原始点明细默认作为辅助排查区域。即使数据很多，也必须分页或虚拟滚动，不允许把所有点直接渲染成页面主体。

### 颜色与密度

已验收 mockup 的视觉性格是“清晰、克制、后台工具”，不是展示型大屏。

颜色约束：

- 页面背景：浅灰蓝。
- 面板背景：白色。
- 主文本：近黑蓝灰。
- 辅助文本：中性灰蓝。
- 主操作和轨迹线：蓝色。
- 使用热力图和用量条：青绿为主。
- 质量提醒：黄色或琥珀色。
- 选中位置点：玫红色。
- 可使用少量紫色区分 Top App 条形图，但不能形成紫色主视觉。

密度约束：

- 面板内边距约 12px 到 18px。
- 指标卡高度约 86px。
- 控件高度约 36px。
- 主工作区间距约 14px。
- 不使用随视口宽度变化的字体大小。
- 文字必须在按钮、指标卡、chip 和表格内完整可读，不能重叠或溢出。

### 响应式要求

桌面端：

- 左导航固定或保持在左侧。
- 筛选条 6 列。
- 指标卡 6 列。
- 手机主工作区 `1fr + 360px`。
- 历史位置主工作区 `1fr + 390px`。
- 图表和下方列表 2 列。

窄屏端：

- 左导航可以变成顶部或普通流布局，但不能遮挡内容。
- 筛选条变成 2 列或 1 列。
- 指标卡变成 2 列或 1 列。
- 主工作区上下堆叠：主视图在上，详情在下。
- 热力图保留横向滚动，不压缩到无法辨认。
- 地图保持固定最小高度，详情在地图下方。

## 页面一：手机记录

### 信息架构

`手机记录` 页面分成五层：

1. 顶部控制区：页面标题、快捷范围、北京时间标识、刷新。
2. 筛选区：设备、分类、App 搜索、是否隐藏系统噪声、粒度、日期范围。
3. 指标区：总时长、日均、目标、App 数、完整度、最近同步。
4. 主工作区：左侧热力图，右侧选中时段详情。
5. 扩展分析区：分类占比、Top App、趋势图、异常、时间线、App 知识库入口。

第一屏必须能回答三个问题：

- 最近 7 天什么时候用得最多？
- 主要花在哪些分类和 App 上？
- 这份数据是否完整可信？

### 热力图重构

当前热力图的问题不是颜色，而是坐标语义错误。新的热力图必须满足：

- 行是日期，默认 7 行；30 天时可以按周分组或虚拟滚动，但不能变成无法阅读的超长墙。
- 列是小时，固定 24 列。
- 单元格只表达强度，不再重复显示小时数字。
- 顶部小时轴可紧凑显示为 `0 1 2 ... 23`，在空间不足时显示 `0 3 6 9 12 15 18 21`。
- 左侧日期显示 `7月8日 今天`、`7月7日 周二` 等中文标签。
- 图例展示 `少 -> 多`，颜色应使用中性底色加青绿或蓝绿强度，不使用大面积强紫、深蓝或单色压迫。
- 低质量或不完整桶可以在格子底部加细条提示，例如黄色代表覆盖不足。
- 选中格使用明显描边，右侧详情面板展示具体内容。

点击热力格后的行为：

- 不改变顶部选择的 7 天范围。
- 不自动把全页面查询缩小到单小时。
- 设置 `selectedBucket` 状态，右侧详情面板展示该时段。
- 下方图表可提供“跟随选中时段”开关，默认不跟随，以免页面跳动。
- 右侧详情中提供“只看这个时段”动作，用户明确点击后才把全局范围缩小。

下钻规则：

- 默认显示小时粒度。
- 点击小时格后，右侧详情可显示该小时内 30 分钟或 15 分钟小条。
- 顶部粒度切到 30 分钟或 15 分钟时，只影响选中日期或局部详情，不应在 7 天全局视图里渲染 672 或 2688 个小格。
- 如用户需要全范围细粒度，应进入“明细模式”或使用虚拟滚动表格，而不是第一屏热力图。

### 选中时段详情

右侧面板展示：

- 时间范围，例如 `7月6日 20:00 至 21:00`。
- 总使用时长，例如 `52分钟`。
- 主导分类，例如 `短视频/娱乐`。
- Top App、切换次数、最长连续、系统噪声状态。
- App 明细条形图：中文名优先，包名次级显示。
- 质量提示：事件覆盖、fallback 占比、是否有短事件被折叠。
- 明确动作：`只看这个时段`、`查看会话`、`管理 App 分类`。

### 分类与 App 可读性

生活分类是主分组，包名是辅助字段。

内置分类：

- 社交通讯
- 短视频/娱乐
- 游戏
- 音乐/音频
- 阅读/资讯
- 学习
- 工作/生产力
- 工具/系统
- 浏览器/搜索
- 出行/地图
- 购物/外卖
- 金融/支付
- 健康/运动
- 相机/创作
- 生活服务
- 未分类

App 显示优先级：

1. 用户手动显示名覆盖。
2. Android 上传的应用标签。
3. 内置常见包名映射。
4. 包名末段的人类化结果。
5. 原始包名。

Top App、时间线和详情面板必须优先展示中文名。包名使用较弱颜色放在下一行，避免主视觉全是技术字符串。

### 图表与分析

深度分析路线要求图表不仅展示“多少”，还展示“变化”和“异常”：

- 分类占比：横向条形图，展示近 7 天分类用量。
- Top App：横向条形图，中文名优先，包名辅助。
- 每日总量趋势：显示每天总使用时长和目标线。
- 小时分布：汇总 7 天中每个小时的平均使用强度。
- 分类趋势：每天各分类变化，可切换堆叠或单分类。
- 切换趋势：每天 App 切换次数或 pickup 次数。
- 上期对比：近 7 天与前 7 天对比。
- 目标进度：支持总时长、分类、单 App 三类目标。
- 异常提示：例如“周日晚间短视频明显高于平时”、“今天同步数据不完整”、“未分类 App 占比偏高”。

异常提示必须可下钻到证据。例如点击异常后高亮相关日期、小时、分类或 App。

### 时间线

时间线默认显示行为块，而非原始会话墙：

- 行为块由相邻或重叠会话聚合而成。
- 每个块展示时间范围、主导分类、总时长、Top App、会话数、质量标记。
- 展开行为块后展示会话列表。
- 展开会话后展示原始事件。
- 加载更多使用分页或游标，不再依赖固定前 500 条。

行为块示例：

- `20:00-21:00 短视频/娱乐 52分钟`
- `18:25-19:30 社交通讯 41分钟`
- `14:10-15:05 工作/生产力 35分钟`

### 系统噪声

默认隐藏：

- 系统桌面、启动器、输入法、系统 UI、快速搜索框。
- 0 到 1 秒的切换噪声。
- 被规则标记为系统噪声的包。

隐藏不是删除。诊断模式下仍可查看它们，并能看到“为什么被隐藏”。

## 页面二：历史位置

### 信息架构

`历史位置` 页面分成五层：

1. 顶部控制区：页面标题、快捷范围、北京时间标识、刷新。
2. 筛选区：设备、日期范围、最大误差、展示图层、是否隐藏已拒绝点、地点/坐标搜索。
3. 指标区：定位点、保留点、活跃跨度、估算里程、停留点、最长停留、平均误差、质量提示。
4. 主工作区：左侧轨迹地图，右侧选中片段详情。
5. 扩展分析区：停留与移动时间线、原始点明细、质量诊断、缺口列表。

第一屏必须能回答：

- 最近 7 天大致在哪里活动？
- 哪些地方停留较久？
- 哪些轨迹片段可信？
- 原始点是否存在低精度、缺口或同步异常？

### 地图主视图

地图成为主视觉，而不是点列表的附属物。

地图图层：

- 轨迹线：按时间连接可用点，按移动片段分段。
- 停留点：使用更大标记，表示某个地点停留超过阈值。
- 误差圈：按水平精度显示，可开关。
- 低质量点：默认隐藏，可开关显示。
- 原始点：默认不全部显示，避免地图噪声；可按选中片段显示。

地图交互：

- 点击轨迹片段，右侧显示移动片段详情。
- 点击停留点，右侧显示停留详情。
- 点击原始点，右侧显示该点的坐标、时间、来源、误差、质量。
- 时间线点击片段时，地图聚焦到对应范围。

### 轨迹与停留聚合

历史位置不能只展示点，应生成用户能理解的片段：

- `停留`：一段时间内位置半径较小，例如 50 到 150 米范围内持续超过 10 分钟。
- `移动`：停留点之间或连续位置变化明显的片段。
- `缺口`：相邻点时间差过大或距离跳跃无法解释的片段。
- `低可信片段`：低精度点占比过高、速度异常、点数不足。

停留卡片展示：

- 停留时间范围。
- 停留时长。
- 估算中心点或地点标签。
- 半径、点数、平均误差。
- 主要来源：GPS、网络、混合。

移动卡片展示：

- 起止时间。
- 估算里程。
- 耗时。
- 平均速度。
- 点数。
- 平均误差。
- 质量说明。

### 位置质量

质量状态不能只通过筛选参数隐藏。UI 需要说明数据为什么可信或不可信。

质量指标：

- 总定位点数量。
- 过滤后保留点数量。
- 被拒绝点数量。
- 平均误差。
- 最大误差。
- GPS / 网络 / 被动来源占比。
- 点间最大时间缺口。
- 速度异常数量。
- 低精度密集区域。

质量提示示例：

- `7月7日 18:49 有 3 个网络定位点误差超过 80 米，已从轨迹线隐藏。`
- `7月5日 02:10 至 08:32 无定位点，可能是系统限制或同步中断。`
- `当前范围定位点较少，里程仅作估算。`

### 原始点明细

原始点列表保留，但不再作为主体验。

默认位置：

- 放在地图下方或右侧详情的折叠区域。
- 只显示当前选中片段的点。
- 全范围原始点需要分页或虚拟滚动。

字段：

- 记录时间。
- 提交时间。
- 纬度/经度。
- 水平误差。
- 来源。
- 速度。
- 海拔。
- 质量。
- 原始 JSON 诊断入口。

## 跨页面联动

手机记录和历史位置不是完全独立。深度分析路线应支持后续联动：

- 同一时间范围与设备选择可以在两个页面间保持。
- 手机记录热力图选中某个小时后，可提供入口查看该小时的位置片段。
- 历史位置选中某段移动或停留后，可提供入口查看同一时间段手机使用行为。
- 今日页或状态页可以复用移动端总体质量摘要。

第一阶段不要求把两个页面合并成一个页面，但数据结构和筛选状态应为后续联动预留。

## API 设计

现有 API 可保留兼容，新增工作台 API 面向聚合查询。

### 通用查询参数

- `rangeStartUtc`
- `rangeEndUtc`
- `timezone`，默认 `Asia/Shanghai`
- `deviceId`
- `includeSystemNoise`
- `includeRejected`
- `minDurationSeconds`
- `maxAccuracyMeters`
- `cursor`
- `pageSize`

### 手机记录 API

`GET /api/v1/mobile/analytics/overview`

返回指标卡、质量摘要、目标、异常和建议。

`GET /api/v1/mobile/analytics/heatmap`

返回热力图桶。后端仍可返回按分类拆分的数据，但前端默认先聚合成 `日期 × 小时` 强度矩阵，并在详情面板展示分类构成。

`GET /api/v1/mobile/analytics/charts`

返回分类占比、Top App、日趋势、小时分布、分类趋势、切换趋势、对比图和目标线。

`GET /api/v1/mobile/analytics/timeline-blocks`

分页返回行为块。

`GET /api/v1/mobile/analytics/timeline-blocks/{blockId}/sessions`

返回行为块下的会话。

`GET /api/v1/mobile/analytics/sessions/{sessionId}/events`

返回会话原始事件。

### 历史位置 API

`GET /api/v1/mobile/location/analytics/overview`

返回定位点数量、保留点数量、活跃跨度、估算里程、停留点数量、最长停留、平均误差、质量提示。

`GET /api/v1/mobile/location/analytics/tracks`

返回地图所需轨迹片段、停留点、缺口和低质量片段。响应应可直接渲染地图，不要求前端在浏览器里重新聚合全部原始点。

`GET /api/v1/mobile/location/analytics/segments/{segmentId}`

返回选中片段详情。

`GET /api/v1/mobile/location/analytics/segments/{segmentId}/points`

分页返回片段内原始点。

`GET /api/v1/mobile/location/history`

继续保留，用于兼容和诊断；新页面不应默认一次性展示全部点。

## 状态与交互

共享状态：

- 时间范围。
- 设备。
- 北京时区。
- 质量过滤。
- 当前选中对象。

手机记录局部状态：

- 分类筛选。
- App 搜索。
- 是否显示系统噪声。
- 热力图选中桶。
- 行为块展开状态。
- 图表是否跟随选中桶。

- 最大误差。
- 是否显示低质量点。
- 地图图层开关。

交互原则：

- 选择不应让页面突然跳走。

## 空状态、加载与错误

空状态：

- 手机记录无数据：说明当前范围无上传记录，并提供查看同步状态入口。
- 历史位置无数据：说明当前范围无定位点，并提示检查 Android 定位权限、上传状态和最大误差筛选。
- 未分类 App 很多：提示进入 App 知识库补充规则。

加载状态：

- 指标卡可以骨架加载。
- 热力图显示固定尺寸骨架，避免布局跳动。
- 地图加载时保留面板尺寸。
- 下钻列表单独显示局部加载，不遮住全页面。

错误状态：

- 接口失败显示中文错误。
- 聚合过期显示“正在重建”或“数据可能滞后”。
- 地图底图失败时仍展示轨迹摘要和点列表，不让页面完全不可用。

## 测试策略

前端测试：

- 默认范围为近 7 天，北京时间。
- 快捷切换今天、7天、30天、自定义。
- 热力图按日期和小时轴渲染，不出现重复小时数字墙。
- 点击热力格只更新详情，不重置全局范围。
- Top App 优先显示中文名，包名作为辅助文本。
- 时间线分页和展开行为正确。
- 历史位置指标、地图层、片段详情、原始点表正确渲染。
- 空状态、错误状态和加载状态中文可读。

后端测试：

- 手机使用聚合按北京时间日界计算。
- 分类规则优先级确定且可重复。
- 系统噪声默认隐藏但诊断可见。
- 热力图聚合不会因分类拆分产生重复坐标渲染问题。
- 行为块分页稳定，不依赖前 500 条。
- 位置点过滤、停留检测、移动片段、缺口检测和质量 flags 有单元测试。
- 位置里程估算处理低精度和跳点。

集成测试：

- Web 与 API 合约覆盖新增 DTO。
- 移动上传后的数据能被聚合查询读取。
- App 分类变更后相关聚合会标记过期或重新生成。
- 位置筛选变更后地图和详情一致。

视觉验收：

- 实现后的页面截图必须能逐项对应“已验收 UI 基线”：共享顶部结构、6 列筛选条、6 个指标卡、主工作区左右布局、下方双面板、时间线和明细区域都必须存在。
- 计划文档必须把“手机记录第一屏布局”“手机记录热力图视觉细节”“手机记录右侧详情”“历史位置第一屏布局”“历史位置地图视觉细节”“历史位置右侧详情”拆成明确任务，不能合并成泛泛的“优化 UI”。
- 桌面 1440px 宽度下，两个页面第一屏都能看到指标、主视图和右侧详情。
- 窄屏下主视图和详情垂直排列，文字不溢出按钮和卡片。
- 热力图轴、图例、选中状态清晰。
- 历史位置地图、轨迹线、停留点、误差提示不互相遮挡。

## 子代理执行要求

后续进入写计划和执行阶段时，必须使用子代理并行工作。计划文档应显式分配子代理任务，最多允许 14 个子代理同时工作，子代理总数不设上限。

建议并行分工：

- 子代理 1：手机记录现有组件与测试盘点。
- 子代理 2：历史位置现有组件与 API 盘点。
- 子代理 3：手机热力图数据形状与前端算法设计。
- 子代理 4：App 展示名、分类和系统噪声规则设计。
- 子代理 5：位置轨迹、停留、缺口聚合算法设计。
- 子代理 6：前端视觉与响应式审查。
- 子代理 7：后端 API 合约和 DTO 审查。
- 子代理 8：测试矩阵和验收脚本设计。
- 子代理 9：GitHub Actions 和发布风险检查。

主代理负责合并决策、写计划、实现集成、运行验证、提交和推送。

## 实施边界

本设计不要求在一个提交中完成所有深度分析，但最终实现不能以轻量修补代替设计目标。后续计划可以拆成多个提交或阶段，但每个阶段都必须朝最终验收目标收敛。

优先顺序建议：

1. 修正中文可读性和热力图结构。
2. 重构手机记录工作台布局和选中详情。
3. 重构历史位置工作台布局。
4. 增加历史位置聚合 API。
5. 增加深度图表、异常、质量和跨页面联动。
6. 完善测试、构建、GitHub Actions 验收。

## 风险与约束

- 位置聚合算法可能需要多轮调参，尤其是停留点半径、速度异常和低精度点处理。
- 热力图数据当前按分类拆分时，前端必须先合并同一日期小时，否则仍可能出现重复坐标。
- App 中文名依赖 Android 元数据和内置映射，仍需允许用户手动覆盖。
- 地图底图依赖网络，必须保留无底图降级视图。
- 大范围原始点和原始事件必须分页或虚拟滚动，不能一次性渲染。
- 北京时间边界必须在后端和前端保持一致，避免跨日错位。

## 交付与验收流程

进入实现前，先基于本设计写详细计划。计划必须包含：

- 最终验收目标。
- 已验收 UI 基线逐项落地清单。
- 子代理并行分工。
- 每阶段文件清单。
- 测试命令。
- 提交策略。
- 推送 `master` 后等待 GitHub Actions 的检查步骤。

实现完成后：

- 运行 `dotnet test Pim.sln`。
- 运行 `npm --prefix src/client-web run build`。
- 运行相关前端测试。
- 检查 `git status --short --branch`。
- 提交到 `master`。
- 推送到 GitHub。
- 等待 GitHub Actions 自动构建并确认结果。

只有本地验证和远端构建状态都被明确报告，才可以声明完成。
