# PIM 技术实现确认审查设计

## 1. 最终目标

建立一条简单规则，替代建设一套开发治理平台：**主代理在请求用户确认一个技术实现细节之前，必须先由独立子代理审查，然后以通俗方式向用户呈现确认卡，由用户决定。**

本设计不引入复杂度账单、评分系统、多阶段审查关口或 CI 脚本。项目地图和无占位符要求作为两个独立问题保留，不与技术确认审查绑定。

### 1.1 目标

- 防止 PIM 项目中反复出现的过度设计——例如为一次日历写回建设 durable execution 框架。
- 保持用户的最终决定权；由用户而非规则替用户判断什么方案过重。
- 将所有技术决定拉回到用户可理解、可选择的层面。
- 确保范围内功能端到端真实可用，不靠假数据或"后期再做"冒充完成。

### 1.2 非目标

- 不代替用户做技术决策。
- 不建设复杂度账单、评分系统、多阶段 gate 或 CI 审批流程。
- 不编写 plan linter 或格式检查脚本（v1 不做）。
- 不限制 plan 篇幅；限制的是未经审查的技术决定，不是页数。
- 不与 PROJECT_MAP.md 耦合；地图只做普通仓库导航，不作为审批关口。
- 不建设方案推荐算法或机制评分模型；判断依靠独立审阅者的证据分析和用户选择。

## 2. 触发条件：什么是"需要确认的技术实现细节"

唯一触发条件是：**主代理准备请求用户确认一个技术实现细节。** 这时必须先由独立子代理审查，再向用户提问。下面的列表只是帮助识别常见技术细节，不是关键词白名单，也不是脚本规则。

**常见例子：**

- 新数据库实体或表结构
- 后台任务、定时器、作业调度
- 状态机或工作流
- 事务 outbox / inbox / CDC
- ETag 或乐观并发冲突策略
- 缓存层（非 ORM 一级缓存）
- 重试 / 恢复 / 幂等机制
- 新框架或 SDK 选型
- 数据迁移策略
- 安全权限或跨端认证
- 跨端通信协议

普通功能描述、需求澄清、文案和纯视觉偏好通常不属于技术实现细节。例如，"页面要显示同步失败原因"是功能效果；"为失败记录新增 outbox 表并由后台状态机恢复"是需要确认的技术实现细节。

**边界判断原则：** 如果用户正在选择"程序内部具体怎样实现"，就是技术实现细节；如果用户只是在说明想看到的效果或视觉偏好，通常不是。存在疑问时，宁可先审查，不把技术决定藏在功能描述里。

## 3. 精确流程

```
主代理发现需要用户确认的技术决定
    |
    v
1. 主代理形成待确认的候选方案，并说明用户目标和相关仓库事实
    |
    v
2. 独立子代理审查方案，并自行找出最简单可行方案作为比较基准
    |
    v
3. 子代理返回通俗确认卡（见第 4 节）
    |
    v
4. 主代理向用户展示确认卡
    |
    v
5. 用户决定：接受 / 采用更简单方案 / 选择其他方案 / 提出修改
    |
    v
6. 将确认结果写入 spec 或 plan
```

**一次确认对应一次审查。** 多个真正不可分割的细节可以作为同一决定审查，但不能用整包批准掩盖多个可独立选择的机制。判断方法是：移除某个机制后，方案如果仍能独立工作，那么该机制应当单独审查和确认。例如，日历同步中的 outbox 和 ETag 冲突处理可以分别增删，应当分别确认。

**全阶段适用：** 本规则不应只在 brainstorming 生效。任何阶段出现新的技术确认点都触发——包括 spec 自审时发现未确认的决定、写 plan 时方案发生变化、实施中发现原方案不可行而需要调整。如果写 spec 或 plan 时新增或改变了尚未确认的技术决定，必须回到步骤 2，不能静默加入。

**implementation plan 可以非常详细。** 限制的是未经审查的技术决定，不是篇幅。plan 中应该详细描述文件路径、复用模块、数据流和测试策略；然后对于其中包含的技术决定，如果属于第 2 节触发范围且尚未被确认，应当触发审查。

**流程示例（以 Outlook 日历写回为例）：**

1. 主代理在 brainstorming 阶段提出：需要将用户对日历事件的修改写回 Outlook。
2. 主代理识别技术触发项：调用 Graph API 存在失败风险，考虑是否需要 outbox + 后台作业自动重试。
3. 主代理以直接调用、失败时提示重试作为比较基准，并识别出 outbox、状态机、ETag、断线恢复四个可独立增删的候选机制。
4. 主代理将四个候选机制分别发给独立子代理审查。
5. 子代理分别返回确认卡；如果当前没有数据不一致、并发覆盖或必须自动恢复的真实证据，就分别建议不引入这些机制。
6. 主代理向用户展示确认卡，用户同意使用简单方案。
7. 主代理将方案写入 spec/plan，plan 中不再出现 outbox 或状态机机制。
8. 实施过程中如果准备新增现有设计之外的 token 刷新、重试或恢复策略，这就是新的技术决定，应当回到审查流程。

## 4. 通俗确认卡模板

子代理审查后输出以下格式的确认卡。必须用普通中文或合适类比，使非专业用户能理解。

```
■ 你要实现的效果
  （一句话描述用户可见的结果）

■ 这个技术方案实际上怎么做
  （用通俗语言或类比解释当前候选方案）

■ 最简单可行方案
  （如果完全不引入额外机制，代码路径是什么样的）

■ 当前候选方案比简单方案多了什么
  （逐项列出新增的机制：新表、队列、状态机、冲突检测等）

■ 为什么可能需要这些额外内容
  （假设的风险场景、想象中可能发生的问题，或已真实发生的故障）

■ 开发、测试、维护和故障排查成本
  （主观但诚实的估算，仅针对本方案的增量部分）

■ 是否过重：合适 / 建议简化 / 需要用户取舍

■ 推荐选项及理由
  （审阅者的明确建议，包括推荐方案及其原因）
```

**关于成本估算：** 开发成本包括增量的编码、测试和调试；测试成本包括为新增机制编写和运行测试的工作；维护成本包括未来修改时理解该机制的认知负担；故障排查成本包括问题发生时定位根因的难度。没有仓库证据时不得编造精确天数，只需诚实说明成本是低、中还是高，以及工作主要增加在哪里。

**审查判断标准：**

- 是否有现实需求或已出过事故，还是仅假设的风险
- 是否已有可复用的能力，新增机制是否必要
- 新增机制是否服务**当前功能**的真实需求，还是为未来预留
- 极端场景（断网、进程崩溃、并发冲突）是否**真的要求**自动恢复，还是人工重试可接受
- 总成本（开发 + 测试 + 长期维护 + 故障排查）是否与个人项目规模匹配

用户保留最终决定权。审阅者认为过重时，必须给出更简单方案和成本对比，不能替用户决定。

## 5. Outlook 日历同步示例

**场景：** 用户在 PIM 日历中修改一个事件的时间，希望同步回 Outlook。

### 简单方案（默认门槛）

| 步骤 | 说明 |
|------|------|
| 1. 预览 | 用户修改后展示修改前后对比卡片（标题、时间、内容变化） |
| 2. 确认 | 用户点击"同步到 Outlook"按钮 |
| 3. 写回 | 程序直接调用 Microsoft Graph PATCH /events/{id} |
| 4. 更新本地 | Graph 返回成功，更新本地数据库状态 |
| 5. 失败处理 | Graph 返回错误时，显示具体错误消息，用户可点击"重试"或"取消" |

新增机制：无。
复用能力：已有的 Microsoft Graph 认证和 HTTP 调用。
相对成本：低。主要工作是预览界面、一次 Graph 写回、成功后的本地更新和失败提示。

### 候选的额外机制（每项分别审查）

下面每一行都是可以独立采用或删除的技术决定，不能作为一个套餐整体确认：

| 新增机制 | 说明 | 假设解决什么 |
|----------|------|-------------|
| 持久化确认单 | 除了预览和确认按钮，再把确认过程保存为可查询的业务记录 | 支持审计或后续异步执行 |
| 事务 outbox | 写请求持久化到 outbox 表，后台作业异步执行 | 进程崩溃时不丢失写请求 |
| 异步状态机 | 作业追踪 Pending → Executing → Completed / Failed 状态 | 允许手动介入失败作业 |
| ETag 并发冲突 | 多人同时修改同一事件时检测冲突并提示用户解决 | 防止覆盖他人修改 |
| 断线幂等恢复 | 网络断开后重连自动重试未完成的请求 | 用户不需要手动重试 |

相对成本：高。除用户界面和 Graph 写回外，还要维护新表、后台执行、状态转换、恢复逻辑、冲突界面以及对应测试。

### 审查通俗解释

"简单方案相当于你改完日期后，程序直接打一个电话给 Outlook 说'改好了'——电话没打通就告诉你没打通，你自己决定什么时候再试一次。这适用于你一个人管自己的日历，很少遇到电话打不通的情况。

如果把上面的额外机制一次性全部加上，就相当于为了偶尔电话打不通，在公司建一套完整的工单追踪系统：每个电话需求先填申请单，提交到调度中台，调度器跟踪每个申请从待处理到完成的状态，如果有人同时打电话还要走仲裁流程。如果你只是一个人改自己的日历，而且很少遇到真的打不通，那套工单系统就是过度设计。"

### 什么情况下值得单独升级某个机制

出现下面的真实条件时，才考虑它对应的机制：

- 已多次出现 Graph API 调用失败后本地与远端数据不一致的**线上事故**
- 用户明确表示"修改后从不记得重试，导致多次数据不同步"
- 该日历被多人共同编辑，真实发生过并发覆盖导致数据丢失

以上任何一个真实证据都没有出现时，简单方案已经足够。即使某个条件出现，也只审查和增加解决该条件的机制，不代表其余机制一起获得批准。

## 6. PROJECT_MAP.md：普通仓库导航

PROJECT_MAP.md 是一个普通仓库导航文件，帮助主代理和新开发者快速了解：

- 系统由哪些表面组成（API、Web、Windows、Android）
- 各模块的位置和职责
- 共享能力在哪里
- 常见改动去哪里改

它与技术审查流程没有强耦合。地图用于**辅助定位**，不是审批材料的一部分。

维护原则：修改对应范围的人或代理在功能变更中同步更新地图（边界、共享能力、验证命令变化时更新），不要求每次提交都改。不存在"地图未更新不得提交"的阻断规则。

地图不被纳入审查流程。不存在地图相关的审批关口。

## 7. 独立补充：无占位符完成规则

范围内功能不能靠以下方式冒充完成：

| 禁止项 | 示例 |
|--------|------|
| 假数据冒充真实数据 | 硬编码 JSON 响应，从未对接真实接口 |
| 空按钮 / 空页面 | 入口存在但点击后无真实功能或返回 404 |
| 骨架声称完成 | 框架搭好但数据接入推迟到"后续阶段" |
| NotImplementedException | 核心路径抛出未实现异常 |
| "后期再做" | 在本次交付范围内标注等待后续实现的子功能 |
| 仅测试或配置文件 | 合并了测试和配置但没有用户可见的功能 |

**允许的内容：** 真实的 loading/empty/error 状态、输入框 placeholder、设计原型（明确标注未完成，不声称已完成）、范围合同中明确声明的阶段性子集（该子集内部必须端到端可用）。

**举例对比：**

| 不允许 | 允许 |
|--------|------|
| 添加了"同步到 Outlook"按钮，但点击后弹出"即将推出" | 按钮在本次范围外，未添加任何入口 |
| API 返回硬编码事件列表，声称"日历列表已完成" | API 真实查询后返回空列表，UI 展示"没有日历事件" |
| 页面路由已注册，内容为空白，注释写"TODO: 接入数据" | 页面路由在本次范围外，路由注册不包含该路径 |
| 添加了数据表迁移但业务代码 throw NotImplementedException | 功能代码写完整，测试覆盖真实数据流的正向路径 |

**如何验证：** 实施完成后，应有一条端到端路径从入口到可观察结果（UI 操作、API 调用、日志输出等），中间不含 mock、stub 或未实现的转接点。测试应覆盖该路径，但不要求全分支覆盖。如果功能依赖于外部服务（如 Graph API），应在真实或沙箱环境中验证过至少一次，不能仅凭单元测试宣称完成。

这条规则独立于技术审查流程，是完成的客观标准。

## 8. AGENTS.md 规则草案

以下规则可供加入 AGENTS.md：

1. **技术决定必须审查后确认**：主代理在向用户确认任何技术实现细节前，必须先由独立子代理审查。

2. **通俗确认卡**：审查结果必须按第 4 节格式输出确认卡，用非专业用户能理解的语言。

3. **一次对应一次**：一个技术确认对应一次审查。不可独立选择的机制可合并，但不能用整包批准掩盖独立决定。

4. **建立比较基准**：独立审阅者必须说明最简单可行方案，再指出候选方案额外增加的机制和成本。

5. **审阅者建议，用户决定**：审阅者认为过重时必须给出更简单方案和成本对比，但不能代用户做决定。

6. **全阶段适用**：brainstorming、spec、plan、实施中方案变更，任何阶段准备向用户确认新的技术决定时都触发审查；不得在已确认方案中静默加入新机制。

7. **禁止占位符交付**：范围内功能必须端到端真实可用，禁止假数据、空入口、NotImplementedException。

8. **PROJECT_MAP.md 日常维护**：边界、共享能力和验证命令变化时同步更新，不作为审批材料。
